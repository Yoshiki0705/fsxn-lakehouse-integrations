# ファイルサーバーのデータを分析・AI で活用する方法 — わかりやすいガイド

> アカウントマネージャー、営業、ビジネスリーダー、実装の詳細ではなく「何ができるか」「なぜそうなるか」を知りたい方向け。

---

## 一言で言うと

**はい、ファイルサーバー（共有ドライブ）上のファイルを Databricks、Athena、Snowflake などの分析プラットフォームで分析できます。ただし、ファイルを丸ごと移動するのではなく、ファイルの「索引カード」を自動作成して検索・分析可能にする仕組みです。**

---

## 図書館にたとえると

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   ファイルサーバー（共有ドライブ） =  図書館の書棚      　      　      │
│   ファイル（PDF、画像、CSV など）    =  実際の本              　　    │
│   分析用の抽出データ                =  索引カード               　   │
│   Databricks Unity Catalog          =  検索システム               │ 
│                                                                 │
│   本は動かしません。                                               │
│   各棚にどんな本があるかを記した「索引カード」を作り、                   │
│   検索システムで誰でも必要な情報を見つけられるようにします。              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

- **本は書棚に残る**（ファイルはファイルサーバーに残る）
- 小さな**索引カード**が作られる（構造化データ: タイトル、著者、分類 — ファイルから抽出）
- **検索システム**（Databricks）で索引カードを検索
- 実際の本が必要になったら書棚に取りに行く（オンデマンドのファイルアクセス）

---

## なぜ直接「接続」できないのか？

短い答え: **Databricks はファイルサーバーの言葉を直接話せないからです。**

ファイルサーバーは NFS や SMB（Windows のエクスプローラーや Linux が使うプロトコル）を使います。Databricks は自分専用のストレージ上にデータがあることを期待します。日本の家電をアメリカのコンセントに差すようなもので、変換アダプターが必要です。

この「変換アダプター」が自動パイプラインです:
1. ファイルサーバーから関連データを**読み取る**（ファイルは移動しない）
2. 有用な情報を**抽出する**（測定値、メタデータ、AI 分類結果）
3. その小さな抽出データを Databricks 対応ストレージに**書き込む**

## データを届ける 3 つの方法

```
┌─────────────────────────────────────────────────────────────────────┐
│                                                                     │
│  ファイルサーバー                                               　     │
│  （数千のファイル:                                                　   │
│   画像、PDF、CSV）                                                 　 │
│         │                                                           │
│         │ ① 対象ファイルを読み取り                                     │
│         ▼                                                           │
│  ┌─────────────────┐                                                │
│  │  処理パイプライン　│  自動処理がファイルから　                          │
│  │                 │  有用な情報を取り出す         　　                 │
│  └────────┬────────┘                                                │
│           │                                                         │
│     ┌─────┼──────────────────────┐                                  │
│     │     │                      │                                  │
│     ▼     ▼                      ▼                                  │
│ ┌────────┐ ┌─────────────┐ ┌─────────────────┐                      │
│ │ Table  │ │検索 Index  　│ │ Databricks Tabe │                      │
│ │(AWS)   │ │(AI 検索用)   │ │(分析用)          │                      │
│ └────────┘ └─────────────┘ └─────────────────┘                      │
│                                                                     │
│  ② ここに保存されるのは「索引カード」のみ — ファイル本体ではない             │
│     通常、元のファイル量の 1% 未満                                   　　│
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

| 方法 | 向いている場面 | 所要時間 | コスト |
|------|-------------|---------|-------|
| **A. スマート抽出**（推奨） | 多様なファイルから構造化インサイトを得たい | 数時間で構築 | 極小（10万ファイルで月 ~$5） |
| **B. 選択同期** | 特定ファイル種別（CSV など）だけが必要 | 1 日で構築 | 小（同期ファイル分のストレージのみ） |
| **C. 全量同期** | ML で全ファイルが必要（画像トレーニングなど） | 1 日で構築 | 大（全ファイルが複製される） |

## どの方法が適しているか？

```
ここから始める:
     │
     ▼
ファイルの「中身」を分析したいですか？
（CSV の数値、PDF のテキストなど）
     │
     ├── はい → 全ファイルが必要？特定種別だけ？
     │              │
     │              ├── 特定種別（CSV、Parquet）→ 方法 B（選択同期）
     │              └── 全ファイル（画像 ML など）→ 方法 C（全量同期）
     │
     └── いいえ、ファイルの「属性情報」だけ
         （何がある、誰のもの、いつ変わった、AI 分類）
          → 方法 A（スマート抽出）
```

**ほとんどのお客様は方法 A から始めます** — まずファイルの発見・分類がしたいのであって、全ファイルのコピーではないからです。

## 費用と期間

### 典型的なスケジュール

| フェーズ | 何をするか | 所要期間 |
|---------|-----------|---------|
| セットアップ | ファイルサーバーとパイプラインを接続 | 1〜2 日 |
| 処理 | パイプラインがファイルを読み取り索引を作成 | 2〜3 日 |
| 運用開始 | 検索・分析が可能に | 継続 |

**合計: 着手から「検索可能」まで 5〜7 営業日**

| 何に払うのか | 月額 |
|------------|:----:|
| ファイルを読み取り分類する AI | ~$65 |
| 検索データベース | ~$42 |
| 処理基盤（パイプライン自体） | ~$7 |
| **合計** | **~$114/月** |

ファイルはファイルサーバーに残るため、ファイル自体の追加ストレージ費用はかかりません。

## 「ゼロコピー」の本当の意味

この言葉が最も混乱を招きます。事実を整理すると:

| 「ゼロコピー」とは | それでも作られるもの |
|------------------|-------------------|
| **ファイルは移動しない** — 画像、PDF、動画はファイルサーバーに残る | 小さな**分析用抽出データ**が作られる（ソース 6 GB に対して ~1 MB） |
| 生データの**重複ストレージがない** | メタデータの構造化テーブル（ファイル名、分類、測定値） |
| ファイル全体の**継続的な同期がない** | パイプラインは新規/変更ファイルに対して継続実行 |

**たとえ**: Google がウェブサイトをインデックスする時、ウェブサイトはそのまま残ります。Google が作るのはインデックス（元のサイズのごく一部）であり、それにより検索可能になる。同じ原理です。

## ビジネス担当者からのよくある質問

**Q: セキュリティは大丈夫？**
はい。ファイルは AWS アカウントの外に出ません。パイプラインはプライベートネットワーク内でファイルを読み取り、抽出データも自分の AWS ストレージに書き込みます。既存システムと同じセキュリティルールでアクセス制御されます。

**Q: 既存の業務ワークフローへの影響は？**
ありません。Windows ファイル共有や Linux マウントを使っている人は今まで通りです。分析パイプラインは追加的な仕組みで、ファイルを変更しません。

**Q: Databricks は必須？**
必須ではありません。分析用の抽出データは以下からもクエリできます:
- Amazon Athena（サーバーレス SQL、クエリごとの課金）
- Amazon QuickSight（ダッシュボード）
- Snowflake（既に利用中の場合）
- 標準的なデータ形式を読む任意のツール

Databricks は高度な ML/AI 機能が必要な場合、または組織で既に利用中の場合に適しています。

**Q: お試しはできる？**
はい。100〜1,000 件のサンプルファイルを使った実証実験（PoC）は約 1 週間、費用は $50 未満です。本番ファイルサーバーへの変更は一切不要です。
