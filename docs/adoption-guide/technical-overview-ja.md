# FSx for ONTAP × AI メタデータカタログ: テクニカルオーバービュー

> ゼロコピーメタデータカタログパイプラインのアーキテクチャと検証メトリクス。

---

## 課題の背景

- **NAS データの不可視性**: エンタープライズファイルサーバー上の非構造化ファイルは、分析プラットフォームから検索・発見できない。
- **データコピーのオーバーヘッド**: 分析のために NAS データを S3 へコピーすると、ストレージコストが倍増し、継続的な同期の複雑さが生じる。
- **スケールする手動分類の限界**: 部門横断で日々数千件変更されるファイルに、人手でのタグ付けは追従できない。

---

## ソリューションアーキテクチャ

```
┌─────────────────┐     ┌──────────────┐     ┌─────────────────┐     ┌──────────────┐     ┌─────────────────┐
│  FSx for ONTAP  │────▶│  S3 Access   │────▶│  AI Pipeline    │────▶│  S3 Tables   │────▶│  Analytics      │
│  (NFS/SMB)      │     │  Point       │     │  (Bedrock/      │     │  (Iceberg)   │     │  (Athena/EMR/   │
│                 │     │  (read-only) │     │   Lambda)       │     │              │     │   OpenSearch)   │
│  ファイル原本    │     │  ゼロコピー   │     │  分類 +         │     │  メタデータ   │     │  検索 +         │
│                 │     │  ストレージ   │     │  埋め込み       │     │  のみ         │     │  クエリ         │
└─────────────────┘     └──────────────┘     └─────────────────┘     └──────────────┘     └─────────────────┘
        │                                                                                          │
        └──────────────── ファイルは移動しない（ゼロコピーストレージ原則）─────────────────────────────┘
```

**ゼロコピーストレージ**: S3 Access Point は FSx for ONTAP ボリューム上のファイルをインプレースで読み取る。処理時に Lambda メモリ上で一時的にファイル内容にアクセスするが、ファイルバイト自体はソース FSx for ONTAP ボリューム外に永続化されない。

## 検証メトリクス（PoC）

| メトリクス | 値 | 注意事項 |
|-----------|-------|---------|
| エンドツーエンドパイプライン時間 | **42 秒**（検出 → 分類 → 登録 → 検索可能） | 単一ファイル; バッチスループットは並行性に依存 |
| ファイルあたりコスト | **$0.07**（Lambda + Bedrock + S3 Tables） | 約 100KB–1MB 文書想定; ファイルサイズにより変動 |
| 月額コスト（10万ファイル、日次1K変更） | **$114/月**（アイドル: ~$5/月） | デフォルト OpenSearch OCU 配分想定 |
| S3 フルコピー対比ストレージオーバーヘッド | **約 95% 削減** | 代替が S3 フルコピーの場合のみ該当 |
| 分類信頼度 | **0.94**（PoC 平均） | テストデータセットのみ; 本番精度はファイル種別・言語・ドメインにより変動 |

## プラットフォーム統合状況

| プラットフォーム | ステータス | 備考 |
|----------------|-----------|------|
| Amazon Athena | ✅ 検証済み | S3 Tables Iceberg 直接クエリ; アイドル後コールドスタート 3–5 秒 |
| Amazon EMR (Spark) | ✅ 検証済み | ネイティブ Iceberg テーブル読み書き |
| Amazon OpenSearch | ✅ 検証済み | ベクトル + キーワード検索; アイドル後ウォームアップ 10–30 秒 |
| Snowflake | ✅ Cortex File AI 検証済み | Iceberg カタログ直接クエリは Snowflake 側の機能サポート待ち |
| Databricks | 評価中 | DataSync 経由または Foreign Catalog（2026-06 時点で進化中） |

## 制約事項

| 項目 | 詳細 |
|------|------|
| S3 AP はこのパイプラインで読み取り専用 | 分析サービスから FSx for ONTAP ボリュームへの書き戻し不可（API レベルでは書き込みサポート） |
| S3 AP 経由の S3 Event Notifications 非対応 | Snowpipe、EventBridge、バケット通知のトリガー不可 |
| FPolicy レイテンシ | NAS クライアントのファイル操作に ~1–5ms 付加 |
| Lambda 一時処理 | ファイル内容は Lambda メモリを通過 — 永続化はされないが、処理層では「ゼロデータ移動」ではない |
| Bedrock 精度のばらつき | ファイル種別、言語ミックス、ドメイン用語により分類品質が変動 |
| S3 Tables 成熟度 | GA 2024年12月; 一部クロスプラットフォーム統合はまだ進化中 |
| Athena コールドスタート | アイドル後の初回クエリで 3–5 秒追加 |
| OpenSearch ウォームアップ | サーバーレス OCU 割り当て: 長時間アイドル後 10–30 秒 |

## このパターンが適さないケース

| シナリオ | 代替案 | 理由 |
|---------|--------|------|
| データが S3 で生成される（NAS 起源なし） | S3-native + Glue | データが既に S3 にあればゼロコピーの利点なし |
| 少量ファイル（<5K、変更頻度低） | DataSync + S3 | 運用が単純; イベント駆動検出は不要 |
| S3 Event Notifications が必要 | S3 Standard | S3 AP は Event Notifications 非対応 |
| 分析からストレージへの書き戻しが必要 | S3 Standard | S3 AP はこのパイプラインで読み取り専用 |
| FSx for ONTAP 未導入 | 導入コストを先に評価 | 本ソリューションは FSx for ONTAP 導入済みまたは計画を前提 |

詳細な選定フローは [アーキテクチャ比較](./architecture-comparison-ja.md) を参照。
