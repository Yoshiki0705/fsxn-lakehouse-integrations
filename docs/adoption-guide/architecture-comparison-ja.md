# アーキテクチャ比較: 非構造化データ分析へのアプローチ

> NAS 上の非構造化ファイルデータを分析プラットフォームからクエリ可能にするアプローチの比較ドキュメント

---

## 概要

本ドキュメントは、非構造化ファイルデータ（NAS）を分析・AI サービスに接続するためのアーキテクチャアプローチを比較します。各アプローチには正当なトレードオフがあり、最適な選択はデータの出自、アクセスパターン、ファイル数量、既存ツール環境に依存します。

---

## アプローチ概要

| アプローチ | データ移動 | イベント駆動 | マルチプロトコル | 最適な用途 |
|----------|:--------:|:---------:|:----------:|----------|
| FSx for ONTAP + S3 Access Point | ゼロコピーストレージ* | FPolicy | NFS/SMB/S3 | 既存 NAS ワークロード、デュアルアクセス |
| S3 ネイティブ + Glue | S3 に生まれたデータ | S3 Events | S3 のみ | クラウドネイティブデータ、新規アプリ |
| DataSync + S3 | フルコピー | スケジュール | ソース NAS → S3 | 少量ファイル、シンプルな一方向同期 |
| Databricks Unity Catalog | S3 コピー必須 | — | S3/ADLS | 構造化/半構造化レイクハウス |

*ゼロコピーストレージ: S3 Access Point が FSx for ONTAP ボリュームからファイルをその場で読み取ります。処理時には Lambda メモリ内で一時的にファイルコンテンツにアクセスします。ファイルバイトはソース FSx for ONTAP ボリューム外に永続化されません。

---

## 詳細比較

### FSx for ONTAP + S3 Access Point（本ソリューション）

**仕組み:**
- ファイルは FSx for ONTAP ボリューム上に残る
- S3 Access Point が分析サービスへの読み取りアクセスを提供
- FPolicy がファイル作成/変更/削除イベントを検知
- Lambda が S3 AP 経由でファイルを処理、Bedrock が分類、メタデータは S3 Tables（Iceberg）に格納

**強み:**
- ストレージのデータ重複なし — 外部フットプリントはメタデータのみ
- ユーザーは NFS/SMB アクセスを継続、分析は同一データに S3 AP 経由でアクセス
- FPolicy によるリアルタイムイベント検知（ポーリング不要）
- AWS 分析スタックとのネイティブ統合（Athena、EMR、OpenSearch）
- ONTAP 機能（SnapMirror、FlexClone、ストレージ効率化）がそのまま利用可能

**制限事項 & 考慮事項:**
- S3 AP はこのパイプラインでは読み取り専用で使用（**書き込みもサポート**） — 分析ツールから FSx for ONTAP ボリュームへの書き戻しは不可
- S3 Access Point は **S3 Event Notifications をサポートしない**（Snowpipe、EventBridge ルール等の自動トリガー不可）
- FPolicy は NAS クライアントに対し ~1–5ms のレイテンシオーバーヘッドを追加
- Lambda 処理: ファイルコンテンツは Lambda メモリを通過（一時的、永続化されないが、処理レイヤーでは「ゼロデータ移動」ではない）
- Bedrock 分類精度はファイルタイプ、言語構成、ドメイン用語により変動（テストデータセットでの PoC 精度。本番精度は異なる）
- ストレージプラットフォームとして FSx for ONTAP が必要

---

### S3 ネイティブ + Glue クローラー

**仕組み:**
- データは最初から S3 に存在（クラウド生まれ）
- Glue クローラーがスキーマを検出、Athena/EMR が直接クエリ
- S3 Event Notifications が処理パイプラインをトリガー

**強み:**
- データが既に S3 にある場合、最もシンプルなアーキテクチャ
- S3 Event Notifications の完全サポート（Snowpipe、EventBridge、Lambda トリガー）
- ファイルシステムオーバーヘッドなし — 純粋なオブジェクトストレージ
- 最も広いエコシステムサポート（全分析ツールが S3 を読める）

**こちらが適切な場合:**
- データがクラウドで生まれたもの（アプリケーションログ、IoT ストリーム、エクスポート）
- 既存 NAS アクセス要件がない
- S3 Event Notifications による下流自動化が必要
- オブジェクトネイティブワークロード（大容量ファイル、追記のみ、ランダムアクセスなし）

**制限事項:**
- 既存 NAS ワークロードには全データ移行が必要
- ファイルシステムセマンティクスなし（権限、ディレクトリ構造、ファイルロック）
- Glue クローラーはバッチ型（リアルタイムではない）
- NAS がプライマリデータソースの場合、継続的な同期の複雑さ

---

### DataSync + S3

**仕組み:**
- AWS DataSync が NAS から S3 へスケジュールでファイルをコピー
- S3 上のコピーに対して標準的な S3 処理パイプライン（Glue、Athena など）が動作

**強み:**
- 最小限の設定でシンプルな一方向同期
- あらゆる NFS/SMB ソースで動作（FSx for ONTAP に限定されない）
- 変更頻度が低い中小規模のファイルセットに適切

**こちらが適切な場合:**
- ファイル数が少ない（<10,000 ファイル）でイベント駆動検知が過剰
- 変更頻度が低い（バッチ更新、夜間同期で十分）
- S3 への書き戻し機能が必要（分析が S3 に出力を書き込める）
- ソース NAS が FSx for ONTAP ではない

**制限事項:**
- 全データ重複（ストレージコスト 2 倍）
- 同期遅延 — リアルタイムではない（スケジュールまたは手動トリガー）
- 個別ファイル変更のイベント駆動検知なし
- 継続的なデータ転送コスト

---

### Databricks Unity Catalog

**仕組み:**
- データはクラウドオブジェクトストレージ（S3、ADLS、GCS）に存在する必要がある
- Unity Catalog が構造化/半構造化レイクハウステーブルのガバナンスを提供
- NAS ファイルは事前に S3 へコピーが必要

**強み:**
- 構造化分析と ML ワークロードに優秀
- 強力なガバナンス（行/列レベルセキュリティ、リネージ、監査）
- Spark ベースツールとコネクタの大規模エコシステム

**制限事項:**
- NAS 上のファイルには S3 コピーが必要
- 表形式データに焦点 — 非構造化ファイル分類のネイティブサポートは限定的
- S3 Tables に対する Foreign Catalog 統合はまだ発展途上
- コンピュートに追加 DBU コスト

---

## このアプローチが適さないケース（FSx for ONTAP + S3 AP）

以下の場合、本ソリューションは**最適ではありません**：

| シナリオ | より適切な代替案 | 理由 |
|----------|---------------|------|
| データが S3 で生まれた（NAS 起源なし） | S3 ネイティブ + Glue | データが既に S3 にあればゼロコピーストレージのメリットなし |
| オブジェクトネイティブワークロード（大容量メディア、追記のみログ） | S3 + S3 Events | S3 Event Notifications で Snowpipe/EventBridge トリガー可能 |
| 少量ファイル（<5,000 件、低頻度変更） | DataSync + S3 | DataSync の方が運用がシンプル。イベント駆動検知は不要 |
| 分析からストレージへの書き戻しが必要 | S3 Standard | S3 AP は読み取り専用。FSx for ONTAP への結果書き戻し不可 |
| 構造化/表形式データのみ | Databricks / Glue | Unity Catalog や Glue Data Catalog が AI 分類なしで表形式データを処理 |
| FSx for ONTAP の既存デプロイがない | まず FSx for ONTAP 導入コストを評価 | 本ソリューションは FSx for ONTAP が導入済みまたは計画中を前提 |

---

## 本ソリューションで使用する ONTAP プラットフォーム機能

| 機能 | ソリューションでの役割 |
|------|-------------------|
| S3 Access Point | Lambda/分析サービスからの読み取り専用ファイルアクセス（ゼロコピーストレージ） |
| FPolicy | リアルタイムファイルイベント検知（作成/変更/削除/リネーム）。~1–5ms のレイテンシ追加 |
| SnapMirror | DR およびマルチリージョンデプロイ向けクロスリージョンレプリケーション |
| FlexClone | テスト/開発環境向けのスペース効率の良いコピー |
| ストレージ効率化 | 重複排除 + 圧縮で実効ストレージコストを削減 |
| マルチプロトコル | NFS + SMB + S3 を同一データ上で提供 — ユーザーと分析が共存 |

## 判断フレームワーク

```
データは既に S3 に生まれたもので、NAS アクセスが不要？
  → はい: S3 ネイティブ + Glue を使用（最もシンプル）
  → いいえ: 続行

ファイル数が少ない（<5K）で変更頻度が低い？
  → はい: DataSync + S3 を検討（運用がシンプル）
  → いいえ: 続行

S3 Event Notifications が必要（Snowpipe、EventBridge トリガー）？
  → はい: S3 ネイティブが必須。S3 AP は Event Notifications 未対応
  → いいえ: 続行

FSx for ONTAP は既にデプロイ済み（または計画中）？
  → はい: FSx for ONTAP + S3 AP アプローチ — ゼロコピーストレージ、FPolicy 駆動
  → いいえ: まず他の理由で FSx for ONTAP 導入が正当化されるか評価

分析ツールがストレージに結果を書き戻す必要がある？
  → はい: S3 Standard（S3 AP は読み取り専用）
  → いいえ: FSx for ONTAP + S3 AP は互換性あり
```

## 制限事項 & 考慮事項（本ソリューション）

| 項目 | 詳細 |
|------|------|
| S3 AP 読み取り専用 | 分析サービスから S3 AP 経由で FSx for ONTAP ボリュームへの書き戻し不可 |
| S3 Event Notifications 非対応 | S3 AP 経由で Snowpipe、EventBridge ルール、S3 バケット通知のトリガー不可 |
| FPolicy レイテンシ | NAS クライアントへのファイル操作ごとに ~1–5ms 追加 |
| Lambda 一時的アクセス | 処理中にファイルコンテンツが Lambda メモリを通過。永続化されないが「ゼロデータ移動」ではない |
| Bedrock 精度 | テストデータセットでの PoC 精度。本番精度はファイルタイプ、言語構成、ドメイン用語により変動 |
| S3 Tables の成熟度 | 2024年12月 GA — 一部のクロスプラットフォーム統合（Snowflake Iceberg カタログ、Databricks Foreign Catalog）はまだ発展途上 |
| Athena コールドスタート | アイドル後の最初のクエリ: 3–5 秒の追加レイテンシ |
| OpenSearch ウォームアップ | アイドル後の Serverless OCU 割り当てに 10–30 秒かかる場合あり |
