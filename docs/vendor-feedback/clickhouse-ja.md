# フィードバック: ClickHouse

対象: Amazon FSx for NetApp ONTAP S3 Access Point から読み取る `s3()` テーブル関数。
2026-05-26、ClickHouse 26.5.1 で計測。
[エビデンス](../../verification-pack/clickhouse/evidence/2026-05-26/evidence-record.yaml)

## サマリー

所見は1件で、ストレージ互換性の差分ではなく認証情報の扱いの差分です。ClickHouse は
Access Point エイリアスをバケット名として認識し、パススタイルの URL 形式も動作しました。
テストを阻害したのは、`s3()` に STS セッショントークンを受け取る手段がなく、一時的な
認証情報を一切使えないことです。

これは FSx for ONTAP 固有の問題ではありません。ロールを引き受けた認証情報を用いる
ClickHouse からのあらゆる S3 アクセスに当てはまります。

---

## 所見: `s3()` が STS セッショントークンを受け取れない

STS の一時認証情報で3つの方法を試行しました。

| 試行 | 結果 |
|---|---|
| `SETTINGS s3_session_token = ...` | `UNKNOWN_SETTING: s3_session_token is neither a builtin setting` |
| 環境変数 `AWS_SESSION_TOKEN` | `HTTP 400 Bad Request — Failed to get object info`。環境変数は `s3()` に拾われなかった |
| STS 出力の `access_key` + `secret` を明示 | `HTTP 400` — STS の認証情報は付随するセッショントークンなしには無効であり、それを渡すパラメータが存在しない |

3行目が核心です。STS は3つの値を発行し、`s3()` は2つを受け取ります。上の2行は3つ目を
別の経路で供給する試みであり、いずれも S3 クライアントに到達しません。

### 動作したこと

問題を認証情報だけに絞り込めるため記録します。

| 観測項目 | 内容 |
|---|---|
| パススタイル URL | `https://s3.<region>.amazonaws.com/<bucket>/<key>` が受理された |
| Access Point エイリアスをバケット名として使用 | ClickHouse が特別な処理なしに認識した |

したがって読み取りパス自体は成立見込みがあります。認証のみが阻害要因でした。

## 動作すると見込まれるが未テスト

| 認証情報のソース | 動作すると考える理由 | ステータス |
|---|---|---|
| IAM ユーザーの長期アクセスキー | セッショントークンが関与しない。`s3('url', 'ACCESS_KEY', 'SECRET_KEY', 'Parquet')` | 未テスト（UNV-013） |
| IMDS 経由の EC2 インスタンスプロファイル | ClickHouse は IMDS に対応しており、URL 内にトークンを必要とせず認証情報を供給する | 未テスト |
| IAM ロール信頼を用いた ClickHouse Cloud | クロスアカウントのロール引き受けを `s3()` のパラメータではなくプラットフォームが処理する | 未テスト |

いずれも実行していません。本プロジェクトでは現在 ClickHouse インスタンスを稼働させておらず、
Docker でのテストは利用可能だった STS 認証情報を使いました。結果ではなく見込みとして
記載しています。

## あると助かること

| 提案 | 根拠 |
|---|---|
| `s3()` にセッショントークンのパラメータまたは設定を追加する | ロールを引き受けた認証情報は、AWS でスコープと有効期限を限定した S3 アクセスを付与する通常の方法です。代わりに IAM ユーザーの長期キーを要求することは、AWS のガイダンスが概して推奨しない認証情報タイプへ利用者を向かわせます |
| IMDS または認証情報プロバイダチェーンが想定される答えであれば、`s3()` のドキュメントに明記する | 現在のドキュメントはキーとシークレットのパラメータを説明しており、それが選択肢であるように読めます。一時認証情報についてプロバイダチェーンを指す注記があれば、試行の向きが変わります |

## 位置づけに関する補足

本リポジトリではこれを低優先度として記録しています。順位付けを製品への評価と誤解されない
よう、理由を述べておきます。

ここで ClickHouse が登場する製造業のユースケースにおける役割は、Kafka からのリアルタイム
品質分析、すなわちホットパスです。FSx for ONTAP S3 Access Point から履歴データを読むことは
コールドパスの関心事であり、バッチでのエンリッチメントと事後分析にあたります。ホットパスに
ついては Kafka から直接消費する Materialized View が適切な設計で、S3 アクセスは関与しません。

したがって認証情報の差分は、このアーキテクチャにおける ClickHouse の副次的な用途を制約
しており、主たる用途を制約していません。実際の差分であり解消する価値はありますが、
ClickHouse を選ぶ理由となっている役割を阻害はしていません。

別途、[BLK-003](../ja/blocker-tracker.md) により `S3Queue` エンジンは Access Point から直接
取り込めません。S3 Event Notifications に依存しており、それが発行されないためです。
DataSync で供給される標準 S3 バケットに対する `S3Queue` が利用可能な経路ですが、これも
本プロジェクトでは未テストです（UNV-015）。
