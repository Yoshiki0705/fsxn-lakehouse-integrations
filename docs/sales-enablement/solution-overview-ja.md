# FSx for ONTAP × AI メタデータカタログ: ソリューション概要

> フィールドエンジニア・ソリューションアーキテクト向けテクニカル概要

---

## 課題

- **NAS データはダークデータ**: ファイルサーバー上の非構造化データは検索・分析不能。何がどこにあるか把握できない
- **データコピーはコスト高**: 分析のための S3 コピーでストレージ費用が倍増。100TB = S3 Standard だけで月額 ~$2,280 以上
- **手動分類はスケールしない**: 人手によるファイルタグ付けは日々数千件の変更に追従不可能

---

## ソリューションアーキテクチャ

```
┌─────────────────┐     ┌──────────────┐     ┌─────────────────┐     ┌──────────────┐     ┌─────────────────┐
│  FSx for ONTAP  │────▶│  S3 Access   │────▶│  AI Pipeline    │────▶│  S3 Tables   │────▶│  Analytics      │
│  (NFS/SMB)      │     │  Point       │     │  (Bedrock/      │     │  (Iceberg)   │     │  (Athena/EMR/   │
│                 │     │  (読み取り専用)│     │   Lambda)       │     │              │     │   OpenSearch)   │
│  ファイル原本    │     │  ゼロコピー   │     │  分類 + 埋込    │     │  メタデータ   │     │  検索 + 分析    │
│                 │     │  ストレージ   │     │                 │     │  のみ        │     │                 │
└─────────────────┘     └──────────────┘     └─────────────────┘     └──────────────┘     └─────────────────┘
        │                                                                                          │
        └──────────────── ファイルは移動しない（ゼロコピーストレージ原則）───────────────────────────┘
```

**ゼロコピーストレージ**: S3 Access Point が FSx for ONTAP ボリュームからファイルをその場で読み取ります。処理時には Lambda メモリ内で一時的にファイルコンテンツにアクセスします。ファイルバイトはソース FSx for ONTAP ボリューム外に永続化されません。

## 検証済み指標

| 指標 | 値 | 注意事項 |
|------|-----|---------|
| エンドツーエンド処理時間 | **42 秒**（検知→分類→登録→検索可能） | 単一ファイル。バッチスループットは並行度に依存 |
| 1 ファイルあたりコスト | **$0.07**（Lambda + Bedrock + S3 Tables） | ~100KB–1MB ドキュメント前提。ファイルサイズ別コスト表参照 |
| 月額コスト（100K ファイル、1K/日変更） | **$114/月**（アイドル時: ~$5/月） | デフォルト OpenSearch OCU 割り当て前提 |
| ストレージコスト（S3 フルコピー比） | **95% 削減** | 代替案が S3 フルコピーの場合のみ該当 |
| 分類信頼度 | **0.94**（PoC 平均） | テストデータセットでの PoC 精度。本番精度はファイルタイプ、言語構成、ドメイン用語により変動 |

## プラットフォーム対応状況

| プラットフォーム | ステータス | 備考 |
|-----------------|-----------|------|
| Amazon Athena | ✅ 検証済み | S3 Tables Iceberg 直接クエリ。アイドル後コールドスタート 3–5 秒 |
| Amazon EMR (Spark) | ✅ 検証済み | Iceberg テーブル ネイティブ読み書き |
| Amazon OpenSearch | ✅ 検証済み | ベクトル + キーワード検索。アイドル後ウォームアップ 10–30 秒 |
| Snowflake | ✅ Cortex File AI 検証済み | Iceberg カタログ直接クエリは Snowflake 側機能対応待ち |
| Databricks | 保留中 | DataSync または Foreign Catalog 経由（発展途上） |

## 制限事項 & 考慮事項

| 項目 | 詳細 |
|------|------|
| S3 AP はこのパイプラインでは読み取り専用で使用（書き込みもサポート） | 分析サービスから FSx for ONTAP ボリュームへの書き戻し不可 |
| S3 AP 経由の S3 Event Notifications 非対応 | Snowpipe、EventBridge、バケット通知のトリガー不可 |
| FPolicy レイテンシ | NAS クライアントへのファイル操作ごとに ~1–5ms 追加 |
| Lambda 一時的処理 | ファイルコンテンツが Lambda メモリを通過。永続化されないが処理レイヤーでは「ゼロデータ移動」ではない |
| Bedrock 精度の変動 | ファイルタイプ、言語構成、ドメイン用語が分類品質に影響 |
| S3 Tables の成熟度 | 2024年12月 GA。一部のクロスプラットフォーム統合はまだ発展途上 |
| Athena コールドスタート | アイドル後の最初のクエリに 3–5 秒追加 |
| OpenSearch ウォームアップ | Serverless OCU 割り当て: 長時間アイドル後に 10–30 秒 |

## 本ソリューションが適さないケース

- データが S3 で生まれたもの（NAS アクセス不要） → S3 ネイティブ + Glue を使用
- 少量ファイル（<5,000 件）で変更頻度が低い → DataSync の方がシンプル
- 下流自動化に S3 Event Notifications が必要 → S3 AP はサポートしない
- 分析からストレージへの書き戻しが必要 → S3 AP は読み取り専用
- FSx for ONTAP の既存デプロイがない → まず FSx for ONTAP 導入コストを評価

詳細は[アーキテクチャ比較](./architecture-comparison-ja.md)の判断フレームワーク参照。
