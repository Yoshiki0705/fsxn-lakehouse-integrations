# ADR-012: Schema Evolution Strategy

## Status

**Accepted** — 2026-06-07

## Context / コンテキスト

Manufacturing edge devices evolve over time: new sensor types are added, measurement fields change, quality inspection schemas expand. Schema changes must propagate through the entire pipeline (Edge → Kafka → ClickHouse + Databricks) without breaking existing consumers or requiring coordinated downtime.

製造エッジデバイスは時間とともに進化する：新しいセンサータイプの追加、測定フィールドの変更、品質検査スキーマの拡張。スキーマ変更は既存コンシューマーを壊したり調整されたダウンタイムを必要とせずに、パイプライン全体（Edge → Kafka → ClickHouse + Databricks）に伝搬しなければならない。

## Decision / 決定

Implement **backward-compatible schema evolution** using:
1. **JSON with optional fields** at the Kafka layer (no Schema Registry in PoC; add in production)
2. **Nullable columns + ALTER TABLE** at the ClickHouse layer
3. **Delta Lake mergeSchema** at the Databricks layer

PoC では **JSON + オプショナルフィールド**（Kafka）、**Nullable カラム + ALTER TABLE**（ClickHouse）、**Delta Lake mergeSchema**（Databricks）による**後方互換スキーマ進化**を実装する。

## Schema Evolution Rules / スキーマ進化ルール

### Allowed Changes (Backward Compatible) / 許可される変更（後方互換）

| Change Type | Kafka (JSON) | ClickHouse | Delta Lake | Safe? |
|-------------|-------------|-----------|-----------|-------|
| Add optional field | ✅ Add key (NULL if absent) | ✅ ALTER ADD COLUMN (Nullable) | ✅ mergeSchema | ✅ Yes |
| Add field with default | ✅ Add key with default | ✅ ALTER ADD COLUMN DEFAULT | ✅ mergeSchema | ✅ Yes |
| Widen numeric type (int→long) | ✅ JSON handles naturally | ⚠️ Requires ALTER MODIFY | ✅ Type widening | ✅ Yes |
| Add enum value | ✅ New string value | ✅ String column handles | ✅ String column handles | ✅ Yes |

### Disallowed Changes (Breaking) / 禁止される変更（破壊的）

| Change Type | Why Breaking | Migration Required |
|-------------|-------------|-------------------|
| Remove required field | Old consumers expect it | Deprecate → mark optional → remove after grace period |
| Rename field | Old consumers use old name | Add new field, keep old, remove after migration |
| Change field type (incompatible) | Deserialization failure | Version the schema (new topic or field name) |
| Change field semantics | Silent data corruption | New field name + documentation |

## Implementation by Layer / レイヤー別実装

### Layer 1: Edge → Kafka (JSON)

**PoC approach:** JSON messages with optional fields. Unknown fields are ignored by consumers.

```json
// v1: Original schema
{
  "event_id": "...",
  "timestamp": 1717776000000,
  "device_id": "...",
  "line_id": "...",
  "event_type": "SENSOR_READING",
  "sensor_type": "temperature",
  "value": 42.5,
  "unit": "celsius"
}

// v2: Added fields (backward compatible — old consumers ignore new fields)
{
  "event_id": "...",
  "timestamp": 1717776000000,
  "device_id": "...",
  "line_id": "...",
  "factory_id": "factory-alpha",        // NEW: added in v2
  "event_type": "SENSOR_READING",
  "sensor_type": "temperature",
  "value": 42.5,
  "unit": "celsius",
  "quality_score": 0.98,                // NEW: added in v2
  "calibration_date": "2026-06-01"      // NEW: added in v2
}
```

**Production upgrade path:** Add Confluent Schema Registry or AWS Glue Schema Registry with BACKWARD compatibility mode. This enforces that new schemas can be read by old consumers.

### Layer 2: ClickHouse Schema Migration

```sql
-- Adding new columns (non-breaking, Nullable)
ALTER TABLE factory.sensor_data
    ADD COLUMN IF NOT EXISTS factory_id LowCardinality(String) DEFAULT '',
    ADD COLUMN IF NOT EXISTS quality_score Nullable(Float64),
    ADD COLUMN IF NOT EXISTS calibration_date Nullable(Date);

-- Update Materialized View to include new fields
DROP VIEW IF EXISTS factory.sensor_data_mv;
CREATE MATERIALIZED VIEW factory.sensor_data_mv TO factory.sensor_data AS
SELECT
    JSONExtractString(raw, 'event_id') AS event_id,
    fromUnixTimestamp64Milli(JSONExtractUInt(raw, 'timestamp')) AS timestamp,
    JSONExtractString(raw, 'factory_id') AS factory_id,  -- NEW
    JSONExtractString(raw, 'device_id') AS device_id,
    JSONExtractString(raw, 'line_id') AS line_id,
    JSONExtractString(raw, 'sensor_type') AS sensor_type,
    JSONExtractFloat(raw, 'value') AS value,
    JSONExtractString(raw, 'unit') AS unit,
    JSONExtractFloat(raw, 'quality_score') AS quality_score,  -- NEW
    JSONExtractString(raw, 'calibration_date') AS calibration_date  -- NEW
FROM factory.sensor_data_kafka;
```

**Key property:** JSONExtract returns NULL/default for missing fields in old messages. No backfill required.

### Layer 3: Databricks Delta Lake Schema Evolution

```python
# Enable schema evolution in Structured Streaming
(
    parsed_df.writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "s3://poc-checkpoints/sensor-data/")
    .option("mergeSchema", "true")  # Auto-evolve schema on new columns
    .toTable("manufacturing_catalog.factory_data.sensor_readings")
)
```

**Behavior with mergeSchema=true:**
- New columns in source → automatically added to Delta table schema
- Missing columns in source → filled with NULL in target
- No manual ALTER TABLE needed
- Schema change recorded in Delta transaction log (auditable)

```sql
-- Verify schema history
DESCRIBE HISTORY manufacturing_catalog.factory_data.sensor_readings;
-- Shows schema changes with timestamps and user info
```

## Schema Versioning Strategy / スキーマバージョニング戦略

### PoC: Implicit Versioning

| Indicator | Value | Meaning |
|-----------|-------|---------|
| New field appears in messages | Nullable column auto-added | Schema evolved |
| Field always NULL in recent data | Field deprecated | Mark for removal review |
| `_schema_version` header (optional) | Integer counter | Explicit version tracking |

### Production: Explicit Versioning (Future)

```json
// Kafka message header
{
  "headers": {
    "schema_version": "2",
    "schema_registry_id": "12345"
  }
}
```

| Component | Registry | Compatibility Mode |
|-----------|----------|-------------------|
| Kafka | Confluent Schema Registry or AWS Glue | BACKWARD |
| ClickHouse | Manual DDL versioning (migrations folder) | N/A |
| Databricks | Delta Lake automatic (mergeSchema) | BACKWARD inherent |

## Migration Procedure / マイグレーション手順

### Adding a New Field (Standard Procedure)

```
Step 1: Update edge device code to include new field
        (old devices continue sending without it — OK)
        
Step 2: ClickHouse: ALTER TABLE ADD COLUMN (Nullable)
        ClickHouse: Recreate Materialized View with new JSONExtract
        (Old data: new column = NULL; new data: populated)
        
Step 3: Databricks: No action needed (mergeSchema=true handles automatically)
        (New column appears in Delta table on first message with field)
        
Step 4: Update documentation and glossary
        
Step 5: Update synthetic data generator (generate_events.py)

No coordinated downtime. No consumer restart needed.
Each layer handles the evolution independently.
```

### Removing a Deprecated Field

```
Step 1: Mark field as deprecated in documentation (add deprecation date)
Step 2: Stop sending field from edge devices (after grace period)
Step 3: ClickHouse: Column remains (old data retains value, new data = NULL)
        Optional: ALTER TABLE DROP COLUMN after data expires via TTL
Step 4: Databricks: Column remains in Delta schema
        Optional: Remove via ALTER TABLE DROP COLUMN (Delta Lake 2.0+)
Step 5: Update documentation
```

## Consequences / 結果

### Positive / ポジティブ

- Zero-downtime schema evolution (no consumer restarts)
- Each layer handles evolution independently (loose coupling)
- JSON flexibility allows rapid iteration during PoC
- Delta Lake mergeSchema provides automatic tracking of schema changes
- Backward compatibility ensures old data remains queryable

### Negative / ネガティブ

- No schema enforcement at Kafka level in PoC (add Schema Registry for production)
- ClickHouse Materialized View must be recreated on schema change (brief ingestion pause)
- Nullable columns accumulate over time (need cleanup discipline)
- No automated schema change propagation tooling (manual DDL in PoC)
