# ADR-002: Use ClickHouse for Real-Time Operational Analytics

## Status

**Accepted** — 2026-06-07

## Context / コンテキスト

The manufacturing data platform requires sub-second query performance on high-frequency sensor and quality data for operational dashboards. This is distinct from the governed analytics workload (Databricks) — it serves factory operators who need immediate visibility into production line status, anomalies, and quality metrics.

製造データプラットフォームは、運用ダッシュボード向けに高頻度センサーおよび品質データに対するサブ秒クエリパフォーマンスが必要。これはガバナンス付き分析ワークロード（Databricks）とは異なる — 生産ライン状態、異常、品質メトリクスへの即時可視性を必要とする工場オペレーターに提供する。

## Decision / 決定

Use ClickHouse as the real-time analytics engine for operational dashboards, complementing (not replacing) Databricks for governed analytics.

ClickHouse をリアルタイム分析エンジンとして運用ダッシュボードに使用し、ガバナンス付き分析における Databricks を補完（代替ではなく）する。

## Options Considered / 検討したオプション

| Option | Pros | Cons |
|--------|------|------|
| **ClickHouse** | Sub-second queries on billions of rows; native Kafka consumer; columnar + time-series optimized; MergeTree engine; S3-compatible tiering; manufacturing proven (REF-030) | Requires deployment management; separate from Databricks governance |
| Amazon Timestream | Fully managed; time-series native; serverless | Limited SQL; no Kafka native consumer; less flexible for ad-hoc analytics |
| Databricks SQL Warehouse | Unified with UC governance; no additional system | Not designed for sub-second latency; cold start delays; cost per query |
| Apache Druid | Real-time OLAP; sub-second; Kafka ingestion | Complex operations; smaller ecosystem; limited AWS managed options |
| Amazon Redshift (Streaming) | Managed; SQL; Kafka integration available | Higher latency than ClickHouse for real-time; higher cost for always-on |
| **Databricks Lakehouse//RT** (Reyden) | Millisecond latency on governed Delta/Iceberg; runs natively within Unity Catalog (no separate permissions layer); no CDC/sync pipelines or data copies; up to 16x vs existing serving stacks | Beta (announced 2026-06-16); Databricks-coupled; new/unproven in our environment; manufacturing fit to be validated |

## Consequences / 結果

### Positive / ポジティブ

- Sub-second query latency on high-cardinality manufacturing data
- Native Kafka Engine enables low-latency ingestion (< 5s end-to-end target)
- MergeTree engine optimized for time-series append workloads
- S3BackedMergeTree enables cold data tiering (potentially to FSx for ONTAP S3)
- Proven in manufacturing environments (REF-030, REF-032)
- Complements Databricks — ClickHouse for real-time ops, Databricks for governed batch/ML

### Negative / ネガティブ

- Additional system to operate and monitor
- Data exists in two places (ClickHouse + Databricks Delta) — potential divergence
- ClickHouse tables are NOT governed by Unity Catalog
- Requires separate access control mechanism

## Risks / リスク

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| ClickHouse operational overhead | Medium | Medium | Use ClickHouse Cloud or BYOC |
| Data divergence between ClickHouse and Delta tables | Low | Medium | Both consume from same Kafka topics; define reconciliation SLA |
| ClickHouse not governed by UC | Accepted | Low | ClickHouse serves operational dashboards; governance applies at Databricks layer |

## DAIS 2026 Update (2026-06-16) / DAIS 2026 アップデート

At Data + AI Summit 2026, Databricks announced **Lakehouse//RT** (Beta, powered by the new Reyden engine) — real-time analytics directly on governed Delta Lake / Apache Iceberg tables, with millisecond latency (sub-100ms at ~12,000 qps, up to 16x vs existing serving stacks) and **native Unity Catalog governance**, removing the separate serving layer, CDC/sync pipelines, and data copies. Evidence tier: **Public**; Beta status noted. ([press release](https://www.databricks.com/company/newsroom/press-releases/databricks-launches-lakehousert-bring-real-time-analytics-directly))

**Decision impact**: **unchanged for the PoC** — ClickHouse remains the real-time analytics engine for Phase A. Lakehouse//RT is relevant because it addresses the same operational/real-time need while keeping data UC-governed (closing the "ClickHouse not governed by UC" gap noted above), at the cost of Databricks coupling.

**Plan (try both for knowledge)**: trial **both ClickHouse and Lakehouse//RT** during the PoC to build comparative evidence — latency, cost, governance model, and operational overhead — on the same Kafka-sourced manufacturing data. Re-evaluate the engine choice for **Phase B** based on measured results. This keeps the current decision while ensuring an evidence-based comparison.

DAIS 2026 で Databricks は **Lakehouse//RT**（Beta、新エンジン Reyden）を発表 — governed Delta/Iceberg 上で直接、ミリ秒レイテンシ（約12,000 qps でサブ100ms、既存サービング比 最大16x）かつ **Unity Catalog ネイティブガバナンス**。別サービング層・CDC/同期パイプライン・データコピーを不要にする。evidence tier: **Public**、Beta。

**決定への影響**: **PoC では変更なし** — Phase A のリアルタイム分析エンジンは ClickHouse を継続。Lakehouse//RT は同じ運用/リアルタイム要件を満たしつつ data を UC ガバナンス下に保つ（上記「ClickHouse は UC 非ガバナンス」ギャップを解消する）点で関連。トレードオフは Databricks への結合。

**方針（両方を試して知見化）**: PoC 期間中に **ClickHouse と Lakehouse//RT の両方**を同一 Kafka ソースの製造データで試行し、レイテンシ・コスト・ガバナンスモデル・運用負荷の比較エビデンスを取得。測定結果に基づき **Phase B** でエンジン選定を再評価する。現行決定は維持したまま、エビデンスベースの比較を担保する。
