# ADR-001: Use Kafka as the Factory Event Backbone

## Status

**Accepted** — 2026-06-07

## Context / コンテキスト

The manufacturing data platform requires a mechanism to transport structured events (sensor readings, quality logs, status updates) from edge/factory devices to multiple downstream consumers (ClickHouse, Databricks, monitoring). The chosen backbone must support high throughput, replay, multiple consumers, and exactly-once delivery semantics.

製造データプラットフォームは、エッジ/工場デバイスから複数の下流コンシューマー（ClickHouse、Databricks、モニタリング）へ構造化イベント（センサー読み取り値、品質ログ、ステータス更新）を伝送するメカニズムが必要。選択するバックボーンは、高スループット、リプレイ、複数コンシューマー、正確に1回の配信セマンティクスをサポートする必要がある。

## Decision / 決定

Use Apache Kafka (Amazon MSK or MSK Serverless) as the primary event backbone for factory-generated structured events and lightweight metadata.

Apache Kafka（Amazon MSK または MSK Serverless）を工場生成の構造化イベントおよび軽量メタデータの主要イベントバックボーンとして使用する。

## Options Considered / 検討したオプション

| Option | Pros | Cons |
|--------|------|------|
| **Apache Kafka (Amazon MSK)** | Industry standard for event streaming; durable log with replay; multi-consumer; Databricks native support; ClickHouse native engine; exactly-once semantics | Operational complexity (if self-managed); cost for provisioned capacity |
| Amazon Kinesis Data Streams | Fully managed; tight AWS integration; auto-scaling | No native ClickHouse consumer; limited retention (default 24h–365d); no Kafka protocol compatibility |
| Amazon SQS + SNS | Simple; serverless; no infrastructure management | Not designed for streaming; no replay; no ordering guarantees (standard queues); not suitable for ClickHouse/Databricks streaming |
| Direct HTTP ingestion | Simple point-to-point | No durability; no replay; no multi-consumer; no exactly-once |
| AWS IoT Core + Rules | Native MQTT support; serverless | Limited downstream integrations; requires additional rules for Kafka/ClickHouse routing |

## Consequences / 結果

### Positive / ポジティブ

- Both ClickHouse and Databricks have native Kafka consumers (well-documented, production-proven)
- Replay from any offset/timestamp enables failure recovery without data loss
- Decouples producers from consumers — adding new consumers requires no producer changes
- Schema Registry integration available for schema evolution
- Industry-standard pattern for manufacturing data platforms (REF-033)

### Negative / ネガティブ

- Kafka cluster requires provisioning and monitoring (or MSK Serverless cost management)
- Edge devices need Kafka producer client or MQTT-to-Kafka bridge
- Message size limited (recommended ≤1 MB) — large payloads must be handled separately

## Risks / リスク

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Kafka unavailability loses events | Low (MSK multi-AZ) | High | Edge buffering (to be designed); MSK multi-AZ |
| Message ordering issues | Medium | Medium | Partition key by device_id |
| Schema compatibility breaks consumers | Medium | High | Schema Registry with compatibility checks |
