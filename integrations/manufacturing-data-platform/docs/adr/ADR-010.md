# ADR-010: End-to-End Deduplication Strategy

## Status

**Accepted** — 2026-06-07

## Context / コンテキスト

The architecture uses at-least-once delivery semantics from edge to Kafka (idempotent producer) and from Kafka to consumers (ClickHouse Kafka Engine, Databricks Structured Streaming). While the Kafka producer's idempotence prevents duplicates within a producer session, edge device restarts, network retries at the store-and-forward layer, and Kafka consumer rebalances can introduce duplicates downstream. A unified deduplication strategy is needed across all layers.

アーキテクチャはエッジから Kafka（べき等プロデューサー）および Kafka からコンシューマー（ClickHouse Kafka Engine、Databricks Structured Streaming）まで少なくとも1回の配信セマンティクスを使用する。Kafka プロデューサーのべき等性はプロデューサーセッション内での重複を防ぐが、エッジデバイスの再起動、ストアアンドフォワード層でのネットワークリトライ、Kafka コンシューマーリバランスにより下流で重複が発生し得る。全レイヤーにまたがる統一的な重複排除戦略が必要。

This ADR consolidates the deduplication aspects from ADR-008 (edge layer) and ADR-009 (ClickHouse layer) and adds the Databricks layer.

本 ADR は ADR-008（エッジレイヤー）と ADR-009（ClickHouse レイヤー）の重複排除を統合し、Databricks レイヤーを追加する。

## Decision / 決定

Implement **deterministic event_id generation** at the source and **idempotent deduplication** at each consumer, using the appropriate mechanism for each system.

ソースでの**決定的 event_id 生成**と、各コンシューマーでのシステムに適した**べき等重複排除**を実装する。

## Deduplication Key Design / 重複排除キー設計

```
event_id = f"{device_id}:{epoch_counter}:{sequence_number}"

Example: "factory-alpha-line-A1-sensor-001:1717776000:000042"
```

| Component | Purpose | Uniqueness Scope |
|-----------|---------|-----------------|
| `device_id` | Identifies the physical device | Globally unique per device |
| `epoch_counter` | Unix timestamp of device boot/restart (seconds) | Unique per device lifecycle |
| `sequence_number` | Monotonically increasing counter since last restart | Unique within epoch |

**Properties:**
- Same physical event always generates the same event_id (deterministic)
- Survives retries and replays (same event_id on re-send)
- New device session = new epoch_counter (avoids sequence collision after restart)

## Deduplication by Layer / レイヤー別重複排除

### Layer 1: Edge → Kafka (Produce-Side)

| Mechanism | Configuration | Effect |
|-----------|-------------|--------|
| Kafka idempotent producer | `enable.idempotence=true` | Prevents duplicates from network retries within a single producer session |
| Store-and-forward dedup | Check event_id in SQLite before re-queue | Prevents re-queuing of already-delivered events on restart |

**Remaining risk:** If edge device restarts and replays from store-and-forward queue, events may be re-sent with same event_id → downstream dedup handles this.

### Layer 2: Kafka → ClickHouse

| Mechanism | Configuration | Effect |
|-----------|-------------|--------|
| ReplacingMergeTree | `ENGINE = ReplacingMergeTree(timestamp)` with event_id in ORDER BY | Deduplicates on background merge |
| FINAL keyword | `SELECT ... FROM table FINAL` | Immediate dedup on read (slight cost) |
| OPTIMIZE FINAL | Periodic merge for cleanup | Forces dedup merge |

**Behavior:**
- Short window where duplicates may be visible (between insert and merge)
- Dashboard queries tolerant of brief duplicates (aggregations unaffected)
- Critical queries use FINAL for guaranteed accuracy

### Layer 3: Kafka → Databricks (Delta Lake)

**Selected approach:** `foreachBatch` + MERGE (idempotent upsert)

```python
def upsert_to_delta(batch_df, batch_id):
    """Idempotent upsert: deduplicates within batch and against existing data."""
    from delta.tables import DeltaTable
    
    # Deduplicate within the micro-batch itself
    deduped_batch = batch_df.dropDuplicates(["event_id"])
    
    # MERGE into Delta table (idempotent: same event_id → no-op)
    delta_table = DeltaTable.forName(spark, "manufacturing_catalog.factory_data.sensor_readings")
    
    (delta_table.alias("target")
        .merge(
            deduped_batch.alias("source"),
            "target.event_id = source.event_id"
        )
        .whenNotMatchedInsertAll()
        .execute()
    )

# Streaming with foreachBatch
(
    parsed_df.writeStream
    .foreachBatch(upsert_to_delta)
    .option("checkpointLocation", "s3://poc-checkpoints/sensor-data/")
    .trigger(processingTime="10 seconds")
    .start()
)
```

**Alternative approach:** `dropDuplicatesWithinWatermark` (simpler, less precise)

```python
# Simpler but only deduplicates within watermark window
(
    parsed_df
    .withWatermark("event_timestamp", "1 hour")
    .dropDuplicatesWithinWatermark(["event_id"])
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "s3://poc-checkpoints/sensor-data/")
    .toTable("manufacturing_catalog.factory_data.sensor_readings")
)
```

| Approach | Dedup Guarantee | Performance | Complexity | Recommended For |
|----------|----------------|-------------|-----------|-----------------|
| foreachBatch + MERGE | ✅ Global (all-time) | Medium (MERGE cost) | Medium | Quality events (critical accuracy) |
| dropDuplicatesWithinWatermark | ⚠️ Windowed only | High (append-only) | Low | Sensor data (high volume, brief duplicates acceptable) |

**PoC decision:** Use `dropDuplicatesWithinWatermark` for sensor data (high volume), `foreachBatch + MERGE` for quality events (critical accuracy).

## End-to-End Dedup Flow / エンドツーエンド重複排除フロー

```

───────────                    ─────                ──────────           ──────────
```

## Consequences / 結果

### Positive / ポジティブ

- Deterministic event_id enables deduplication at any layer independently
- No single point of failure for dedup (defense in depth)
- Each system uses its native dedup mechanism (no external dedup service)
- PoC can validate dedup with intentional duplicate injection

### Negative / ネガティブ

- Brief duplicate visibility window in ClickHouse (between insert and merge)
- foreachBatch + MERGE has higher latency than pure append (use selectively)
- event_id generation logic must be consistent across all edge devices
- Clock drift on edge devices can cause event_id ordering issues (NTP required)
