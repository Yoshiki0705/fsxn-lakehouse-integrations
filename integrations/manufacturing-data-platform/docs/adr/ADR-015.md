# ADR-015: Kafka Deployment Strategy — MSK vs Instaclustr on AWS

## Status

**Proposed** — 2026-06-08 (pending Instaclustr SE input)

## Context / コンテキスト

During Phase A deployment, we encountered connectivity challenges between ClickHouse Cloud and MSK:
1. MSK Serverless does not support Multi-VPC connectivity
2. MSK Provisioned requires kafka.m5.large+ for Multi-VPC (~$300/month)
3. Multi-VPC setup is complex and introduces operational overhead

Additionally, for Phase B, we need on-premises Kafka (Instaclustr managed). If the AWS-side Kafka is also Instaclustr, the replication between on-prem and cloud becomes an Instaclustr-managed concern rather than a DIY MirrorMaker 2 or MSK Replicator setup.

Phase A デプロイ中に ClickHouse Cloud と MSK の接続性で課題が発生：
1. MSK Serverless は Multi-VPC connectivity をサポートしない
2. MSK Provisioned は Multi-VPC に kafka.m5.large+ が必要（~$300/月）
3. Multi-VPC セットアップが複雑で運用負荷を追加

Phase B ではオンプレ Kafka（Instaclustr マネージド）が必要。AWS 側も Instaclustr なら、オンプレ⇔クラウド間のレプリケーションは Instaclustr 管理下で統一され、MirrorMaker 2 や MSK Replicator のセルフ運用が不要になる。

## Options / 選択肢

### Option A: MSK Provisioned (current)

```
On-prem Instaclustr Kafka ──── MirrorMaker 2 ────→ AWS MSK Provisioned
                                (self-managed)            │
                                                          ↓ (Multi-VPC PrivateLink)
                                                    ClickHouse Cloud
```

| Pros | Cons |
|------|------|
| AWS-native, integrated monitoring | Multi-VPC complexity (ADR-014) |
| MSK Replicator for managed replication | $300+/month for m5.large |
| Familiar for AWS-only teams | Different vendor on-prem vs cloud |
| | ClickHouse connectivity requires PrivateLink setup |

### Option B: Instaclustr Kafka on AWS (BYOC or Cloud)

```
On-prem Instaclustr Kafka ──── Instaclustr Replication ────→ AWS Instaclustr Kafka
                                (managed by Instaclustr)           │
                                                                   ↓ (same VPC or peering)
                                                             ClickHouse Cloud / Instaclustr CH
```

| Pros | Cons |
|------|------|
| Unified vendor: on-prem + cloud both Instaclustr | Not AWS-native (no CloudWatch native) |
| Instaclustr manages replication (no self-managed MM2) | Requires Instaclustr licensing/contract |
| Same VPC as ClickHouse → no Multi-VPC needed | Less integration with AWS native services |
| NetApp ecosystem alignment (Instaclustr = NetApp) | Additional vendor dependency |
| Consistent operations model across environments | |
| ClickHouse Kafka Engine connects locally (no PrivateLink) | |

### Option C: Self-managed Kafka on EC2

```
On-prem Instaclustr Kafka ──── MirrorMaker 2 ────→ EC2 Kafka (same VPC)
                                (self-managed)            │
                                                          ↓ (same VPC)
                                                    ClickHouse Cloud
```

| Pros | Cons |
|------|------|
| Full control | High operational burden |
| Same VPC as all consumers | No managed service benefits |
| Cheapest (EC2 instances only) | Patching, scaling, monitoring all manual |
| No Multi-VPC needed | Not aligned with PoC goal (minimize ops) |

### Option D: Hybrid — MSK for Databricks, Instaclustr for ClickHouse

```
On-prem Instaclustr Kafka ──→ AWS Instaclustr Kafka ──→ ClickHouse (same VPC)
                          └──→ AWS MSK (via MSK Replicator) ──→ Databricks
```

| Pros | Cons |
|------|------|
| ClickHouse gets local Kafka (no Multi-VPC) | Two Kafka clusters on AWS (cost) |
| Databricks uses MSK natively | Operational complexity of two clusters |
| Best of both worlds | Data duplication across two AWS Kafka clusters |

## Analysis / 分析

### The Core Problem

The root issue is: **ClickHouse Cloud ClickPipes requires either same-VPC access or Multi-VPC PrivateLink to reach Kafka brokers**. MSK Serverless and small MSK Provisioned don't provide this.

### Phase B Perspective

In Phase B, ClickHouse moves to Instaclustr on-prem (same network as on-prem Kafka). The AWS-side ClickHouse Cloud is only needed in Phase A. In production (Phase B), the ClickHouse↔Kafka connectivity problem disappears because both are local.

The only AWS consumer that needs Kafka data in Phase B is **Databricks**. Databricks + MSK works well (Structured Streaming with VPC peering — no Multi-VPC needed, they share VPC).

### Recommendation

**For Phase A (PoC validation):**
- **Continue with MSK Provisioned + Multi-VPC** (already in progress)
- Validates the pattern; acceptable cost for time-limited PoC
- If Multi-VPC setup fails or is too complex → fall back to Option C (EC2 Kafka)

**For Phase B (production target):**
- **Option B: Instaclustr Kafka on AWS** as the primary recommendation
- Unified vendor management with on-prem
- Eliminates Multi-VPC complexity permanently
- Instaclustr manages replication between on-prem and cloud
- **Discuss with Instaclustr SE** during tomorrow's engagement

**Alternative for Phase B if Instaclustr is not available on AWS:**
- MSK Provisioned for Databricks consumption (Structured Streaming works natively)
- ClickHouse runs on-prem (no cloud ClickHouse needed in production)
- MirrorMaker 2 between on-prem Instaclustr Kafka and MSK
