# ADR-005: Use Metadata/Payload Separation for Large Files

## Status

**Accepted** — 2026-06-07

## Context / コンテキスト

Manufacturing environments produce both small structured events (sensor readings, quality metrics, status updates) and large unstructured payloads (inspection images 5–50 MB, video recordings 100 MB–1 GB, technical documents 1–10 MB). A single transport mechanism cannot efficiently handle both. Kafka is optimized for small messages (recommended ≤1 MB); large files would overwhelm topic throughput, increase consumer lag, and complicate retention.

製造環境は小さな構造化イベント（センサー読み取り値、品質メトリクス、ステータス更新）と大容量非構造化ペイロード（検査画像 5–50 MB、動画記録 100 MB–1 GB、技術文書 1–10 MB）の両方を生成する。単一の伝送メカニズムでは両方を効率的に処理できない。Kafka は小メッセージに最適化（推奨 ≤1 MB）; 大容量ファイルはトピックスループットを圧迫し、コンシューマーラグを増大させ、保持を複雑化する。

## Decision / 決定

Separate metadata from payloads:
- **Metadata** (structured events with payload references) flows through Kafka → ClickHouse / Databricks
- **Payloads** (large files) are stored directly on FSx for ONTAP via NFS/SMB/S3
- Kafka messages include a `payload_reference` URI linking to the stored payload

メタデータとペイロードを分離する:
- **メタデータ**（ペイロード参照付き構造化イベント）は Kafka → ClickHouse / Databricks を流れる
- **ペイロード**（大容量ファイル）は NFS/SMB/S3 経由で FSx for ONTAP に直接格納
- Kafka メッセージは格納済みペイロードへリンクする `payload_reference` URI を含む

## Options Considered / 検討したオプション

| Option | Pros | Cons |
|--------|------|------|
| **Metadata/payload separation** | Kafka stays fast and small; payloads stored on optimal medium; independent scaling; proven IIoT pattern | Two systems to coordinate; eventual consistency between event and payload; requires URI resolution |
| Kafka with large messages (increase max.message.bytes) | Single transport; simpler producer | Kafka performance degradation; broker memory pressure; retention explosion; not recommended for >1 MB |
| Kafka + Kafka Connect S3 Sink for payloads | Kafka handles both; S3 Sink offloads | Still flows through Kafka brokers; latency for large files; complex error handling |
| S3 Event Notifications (payload → event) | Serverless; automatic event on upload | Not supported by FSx for ONTAP S3 AP; requires polling or FPolicy alternative |
| All data direct to S3 (no Kafka) | Simple; no streaming infrastructure | No replay; no multi-consumer; no exactly-once; no real-time ClickHouse path |

## Consequences / 結果

### Positive / ポジティブ

- Kafka topics remain small and fast (sub-second ingestion to ClickHouse)
- Payloads benefit from FSx for ONTAP data services (Snapshot, dedup, multiprotocol)
- Independent scaling — Kafka throughput and FSx storage capacity scale separately
- Delta tables in Databricks contain payload_uri columns for downstream access
- Pattern is industry standard for IIoT/manufacturing (REF-033)
- Payloads can be accessed by any protocol (NFS for factory, S3 for analytics, SMB for Windows tools)

### Negative / ネガティブ

- Eventual consistency — payload may be uploaded before or after the Kafka event
- Requires coordination: event must not be processed before payload is available
- URI resolution adds complexity — consumer must handle "payload not yet available" case
- No single transaction spanning event + payload (accept eventual consistency)

## Risks / リスク

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Event arrives before payload upload completes | Medium | Medium | Include `payload_status` field; consumer retries with backoff |
| Payload uploaded but event lost | Low (Kafka durability) | Medium | Orphan detection job; periodic reconciliation |
| URI becomes invalid (file moved/deleted) | Low | High | Immutable URIs; Snapshot-based paths; soft-delete with TTL |
| Checksum mismatch (payload corruption) | Low | High | Verify checksum on read; re-upload from edge buffer |

## Evidence and References / エビデンスと参照
