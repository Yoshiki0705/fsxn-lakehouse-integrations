# ADR-009: Kafka → ClickHouse Connector Specification

## Status

**Accepted** — 2026-06-07

## Context / コンテキスト

ClickHouse needs to consume structured events from Kafka topics (sensor data, quality events, system alerts) with low latency (< 5 seconds end-to-end). Multiple connector options exist, each with different trade-offs in latency, reliability, management overhead, and compatibility with Instaclustr/ClickHouse Cloud.

ClickHouse は Kafka トピック（センサーデータ、品質イベント、システムアラート）から低レイテンシ（エンドツーエンド 5 秒未満）で構造化イベントを消費する必要がある。複数のコネクターオプションが存在し、それぞれレイテンシ、信頼性、管理オーバーヘッド、Instaclustr/ClickHouse Cloud との互換性においてトレードオフがある。

This ADR addresses TSK-003 (Must Fix: Specify Kafka → ClickHouse Connector) from the persona review.

本 ADR はペルソナレビューからの TSK-003（Must Fix：Kafka → ClickHouse コネクタの指定）に対処する。

## Decision / 決定

Use **ClickHouse Kafka Engine** (built-in) as the primary connector for Phase A (ClickHouse Cloud) and Phase B (Instaclustr on-premises). Use **Kafka Connect ClickHouse Sink** as the secondary/alternative path when Kafka Engine is not suitable.

**ClickHouse Kafka Engine**（組み込み）をフェーズ A（ClickHouse Cloud）およびフェーズ B（Instaclustr オンプレミス）の主要コネクターとして使用する。Kafka Engine が適さない場合は **Kafka Connect ClickHouse Sink** を二次/代替パスとして使用する。

## Options Considered / 検討したオプション

| Option | Latency | Management | At-Least-Once | Exactly-Once | ClickHouse Cloud | Instaclustr | Verdict |
|--------|---------|-----------|---------------|-------------|-----------------|-------------|---------|
| **Kafka Engine (built-in)** | Sub-second | Zero (DDL only) | ✅ | ❌ (needs dedup) | ✅ | ✅ | **Selected (primary)** |
| Kafka Connect + ClickHouse Sink | 1-5 seconds | Medium (connector mgmt) | ✅ | ❌ | ✅ (external) | ✅ (bundled) | Secondary |
| ClickPipes (managed) | Sub-second | Zero | ✅ | ❌ | ✅ (Cloud only) | ❌ | Phase A alternative |
| Custom consumer app | Variable | High | ✅ | Possible | ✅ | ✅ | Rejected (unnecessary) |
| Vector (Datadog) | 1-5 seconds | Medium | ✅ | ❌ | ✅ | ✅ | Rejected (extra component) |

## Kafka Engine Design / Kafka Engine 設計

### Architecture Pattern

```
Kafka Topic ───→ Kafka Engine Table ───→ Materialized View ───→ MergeTree Table
                 (virtual consumer)       (transformation)       (queryable storage)
```

### Implementation

```sql
-- Step 1: Kafka Engine table (virtual — reads from Kafka on-demand)
CREATE TABLE factory.sensor_data_kafka (
    raw String
)
ENGINE = Kafka
SETTINGS
    kafka_broker_list = '${KAFKA_BOOTSTRAP_SERVERS}',
    kafka_topic_list = 'factory.sensor-data',
    kafka_group_name = 'clickhouse-sensor-consumer',
    kafka_format = 'JSONEachRow',
    kafka_num_consumers = 3,
    kafka_max_block_size = 65536,
    kafka_skip_broken_messages = 10,
    kafka_thread_per_consumer = 1;

-- Step 2: Destination MergeTree table (queryable, partitioned, ordered)
CREATE TABLE factory.sensor_data (
    event_id String,
    timestamp DateTime64(3),
    factory_id LowCardinality(String),
    device_id LowCardinality(String),
    line_id LowCardinality(String),
    sensor_type LowCardinality(String),
    value Float64,
    unit LowCardinality(String)
)
ENGINE = ReplacingMergeTree(timestamp)
PARTITION BY toYYYYMMDD(timestamp)
ORDER BY (line_id, device_id, sensor_type, timestamp, event_id)
TTL timestamp + INTERVAL 90 DAY TO VOLUME 's3_cold';

-- Step 3: Materialized View (auto-runs on each Kafka batch)
CREATE MATERIALIZED VIEW factory.sensor_data_mv TO factory.sensor_data AS
SELECT
    JSONExtractString(raw, 'event_id') AS event_id,
    fromUnixTimestamp64Milli(JSONExtractUInt(raw, 'timestamp')) AS timestamp,
    JSONExtractString(raw, 'factory_id') AS factory_id,
    JSONExtractString(raw, 'device_id') AS device_id,
    JSONExtractString(raw, 'line_id') AS line_id,
    JSONExtractString(raw, 'sensor_type') AS sensor_type,
    JSONExtractFloat(raw, 'value') AS value,
    JSONExtractString(raw, 'unit') AS unit
FROM factory.sensor_data_kafka;
```

### Quality Events (with payload reference)

```sql
CREATE TABLE factory.quality_events_kafka (
    raw String
)
ENGINE = Kafka
SETTINGS
    kafka_broker_list = '${KAFKA_BOOTSTRAP_SERVERS}',
    kafka_topic_list = 'factory.quality-events',
    kafka_group_name = 'clickhouse-quality-consumer',
    kafka_format = 'JSONEachRow',
    kafka_num_consumers = 2;

CREATE TABLE factory.quality_events (
    event_id String,
    timestamp DateTime64(3),
    factory_id LowCardinality(String),
    device_id LowCardinality(String),
    line_id LowCardinality(String),
    event_type LowCardinality(String),
    measurement_value Nullable(Float64),
    pass_fail Nullable(UInt8),
    payload_reference Nullable(String),
    content_type Nullable(String),
    payload_size_bytes Nullable(UInt64),

ENGINE = ReplacingMergeTree(timestamp)

CREATE MATERIALIZED VIEW factory.quality_events_mv TO factory.quality_events AS
SELECT
    JSONExtractString(raw, 'event_id') AS event_id,
    fromUnixTimestamp64Milli(JSONExtractUInt(raw, 'timestamp')) AS timestamp,
    JSONExtractString(raw, 'factory_id') AS factory_id,
    JSONExtractString(raw, 'device_id') AS device_id,
    JSONExtractString(raw, 'line_id') AS line_id,
    JSONExtractString(raw, 'event_type') AS event_type,
    JSONExtractFloat(raw, 'measurement_value') AS measurement_value,
    JSONExtract(raw, 'pass_fail', 'Nullable(UInt8)') AS pass_fail,
    JSONExtractString(raw, 'payload_reference') AS payload_reference,
    JSONExtractString(raw, 'content_type') AS content_type,
    JSONExtractUInt(raw, 'payload_size_bytes') AS payload_size_bytes,
    JSONExtractString(raw, 'checksum_sha256') AS checksum_sha256
FROM factory.quality_events_kafka;
```

## Deduplication Strategy / 重複排除戦略

The Kafka Engine provides **at-least-once** delivery. Deduplication is handled by:

1. **ReplacingMergeTree** — deduplicates on merge based on ORDER BY key + version column (timestamp)
2. **FINAL keyword** — queries with `FINAL` get deduplicated results immediately
3. **Periodic OPTIMIZE** — forces merges for cleanup: `OPTIMIZE TABLE factory.sensor_data FINAL`

```sql
-- Query with guaranteed dedup (slight performance cost)
SELECT * FROM factory.sensor_data FINAL
WHERE timestamp > now() - INTERVAL 1 HOUR;

-- Query without FINAL (faster, may have rare short-lived duplicates)
SELECT * FROM factory.sensor_data
WHERE timestamp > now() - INTERVAL 1 HOUR;
```

## Error Handling / エラーハンドリング

| Error Type | Kafka Engine Behavior | Mitigation |
|-----------|----------------------|-----------|
| Malformed JSON | `kafka_skip_broken_messages = 10` (skip up to 10 per block) | Monitor skip count; DLQ via separate consumer |
| Kafka broker down | Consumer retries automatically (librdkafka) | Monitor consumer lag |
| ClickHouse overloaded | Backpressure (stops consuming until caught up) | Monitor insert latency |
| Schema mismatch | JSONExtract returns NULL for missing fields | Schema evolution via Nullable columns |
| Consumer group rebalance | Handled by librdkafka | Brief pause during rebalance |

### Dead Letter Queue (DLQ) Pattern

```sql
-- Capture unparseable messages
CREATE TABLE factory.dead_letter_queue (
    received_at DateTime DEFAULT now(),
    topic String,
    raw_message String,
    error_reason String
)
ENGINE = MergeTree()
ORDER BY received_at
TTL received_at + INTERVAL 30 DAY;
```

## Authentication Configuration / 認証設定

### Phase A: MSK Serverless (IAM Auth)

[仮説] ClickHouse Cloud Kafka Engine may not natively support MSK IAM authentication. Validation needed.

**Fallback**: Use MSK with SASL/SCRAM authentication (create SCRAM user in MSK).

```sql
-- SASL/SCRAM configuration
CREATE TABLE factory.sensor_data_kafka (...)
ENGINE = Kafka
SETTINGS
    kafka_broker_list = '${MSK_BOOTSTRAP_SERVERS}',
    ...
    kafka_security_protocol = 'SASL_SSL',
    kafka_sasl_mechanism = 'SCRAM-SHA-512',
    kafka_sasl_username = '${KAFKA_USERNAME}',
    kafka_sasl_password = '${KAFKA_PASSWORD}';
```

### Phase B: Instaclustr On-Prem Kafka

[確認済み] Instaclustr Managed Kafka supports SASL/SCRAM and mTLS. ClickHouse Kafka Engine supports both.

```sql
-- mTLS configuration (Instaclustr on-prem)
CREATE TABLE factory.sensor_data_kafka (...)
ENGINE = Kafka
SETTINGS
    kafka_broker_list = '${INSTACLUSTR_BOOTSTRAP_SERVERS}',
    ...
    kafka_security_protocol = 'SSL',
    kafka_ssl_ca_location = '/etc/clickhouse-server/certs/ca.pem',
    kafka_ssl_certificate_location = '/etc/clickhouse-server/certs/client.pem',
    kafka_ssl_key_location = '/etc/clickhouse-server/certs/client-key.pem';
```

## Performance Expectations / パフォーマンス期待値

| Metric | Target | Basis |
|--------|--------|-------|
| Ingestion latency (Kafka → queryable) | < 2 seconds | Kafka Engine poll interval + MV insert |
| Throughput (single consumer) | ~50K events/sec | REF-030 reference (manufacturing workload) |
| Throughput (3 consumers) | ~150K events/sec | Linear scaling with kafka_num_consumers |
| Query latency (recent data) | < 100ms | MergeTree with appropriate ORDER BY |
| Query latency (with FINAL) | < 500ms | Dedup overhead on read |

## When to Use Kafka Connect Instead / Kafka Connect を使うべき場合

| Scenario | Use Kafka Connect |
|----------|-------------------|
| Complex transformation before insert | ✅ (SMT chains) |
| DLQ routing for failed messages | ✅ (built-in DLQ) |
| Schema Registry integration (Avro) | ✅ (native support) |
| Instaclustr bundled management | ✅ (REF-076) |
| Fan-out to multiple sinks | ✅ (one consumer, multiple sinks) |

Instaclustr bundles the ClickHouse Kafka Connect Sink connector (REF-076), making it a viable managed alternative for Phase B.

## Consequences / 結果

### Positive / ポジティブ

- Zero additional infrastructure (Kafka Engine is built-in to ClickHouse)
- Sub-second ingestion latency
- Simple DDL-based configuration (no external process to manage)
- Works on both ClickHouse Cloud and Instaclustr-managed ClickHouse
- ReplacingMergeTree handles deduplication transparently
- Materialized views provide transformation logic within ClickHouse

### Negative / ネガティブ

- At-least-once only (not exactly-once); requires ReplacingMergeTree for dedup
- Schema changes require DDL migration (ALTER TABLE + recreate MV)
- Error handling limited to skip count (no rich DLQ built-in)
- MSK IAM auth compatibility with ClickHouse Cloud Kafka Engine is unconfirmed
