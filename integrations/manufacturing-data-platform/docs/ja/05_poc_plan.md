## TSK-000: PoC 目標

最小限必要なコンポーネントで AWS 上の製造データプラットフォームアーキテクチャを検証する。

**成功基準:**
1. エッジイベントが Kafka を通じて ClickHouse と Databricks Delta テーブルの両方に到達
2. Delta テーブルが Unity Catalog により管理される
3. 大容量ペイロードが FSx for ONTAP に格納され Delta テーブルから参照される
4. ClickHouse がストリーミングデータに対してサブ秒クエリを提供
5. 障害/リプレイシナリオがテストされ文書化される
6. ClickHouse コールド階層から ONTAP S3 への階層化が検証される（ストレッチゴール）

## フェーズ 1: インフラストラクチャセットアップ

### TSK-001: AWS インフラストラクチャプロビジョニング

単一 AWS リージョン（ap-northeast-1 または us-east-1）に基盤インフラをデプロイ。

**コンポーネント:**
- プライベートサブネット付き VPC（2 AZ にまたがる 4 サブネット）
- コンポーネント間通信用セキュリティグループ
- S3、STS 用 VPC エンドポイント
- Delta Lake ストレージ用 S3 バケット
- Structured Streaming チェックポイント用 S3 バケット

**受入基準:**
- [ ] 正しい CIDR 範囲で VPC がデプロイ済み
- [ ] セキュリティグループが必要なコンポーネント間トラフィックを許可
- [ ] S3 バケットが暗号化有効かつパブリックアクセス禁止で作成済み
- [ ] VPC エンドポイントの動作確認済み

### TSK-002: Amazon MSK クラスターデプロイ

マネージド Kafka クラスターをデプロイ。

**構成:**
- MSK Serverless または Provisioned（PoC 用 m5.large × 3）
- SASL/SCRAM または IAM 認証
- TLS 転送時暗号化
- DES-003 に基づくトピック作成

**受入基準:**
- [ ] MSK クラスターが稼働中かつ健全
- [ ] 認証が設定済みかつテスト済み
- [ ] 正しいパーティション数でトピック作成済み
- [ ] プライベートサブネットからのプロデューサー/コンシューマー接続性確認済み

### TSK-003: ClickHouse デプロイ

リアルタイム分析用 ClickHouse をデプロイ。

**オプション（1つ選択）:**
- ClickHouse Cloud（最速セットアップ）
- ClickHouse BYOC（顧客 VPC 内データ）
- セルフマネージド EC2（最低コスト）

**受入基準:**
- [ ] ClickHouse クラスターが稼働中
- [ ] VPC プライベートサブネットからアクセス可能
- [ ] 認証が設定済み
- [ ] テストクエリが正常実行

### TSK-004: FSx for ONTAP デプロイ

FSx for ONTAP ファイルシステムをデプロイ。

**構成:**
- Single-AZ（PoC コスト最適化）
- SSD ストレージ: 1 TB
- スループットキャパシティ: 128 MB/s（最小）
- NFS および ONTAP S3 有効の SVM
- DES-007 に基づくボリューム

**受入基準:**
- [ ] ファイルシステム作成済みかつアクセス可能
- [ ] NFS エクスポートが設定済みかつマウント可能
- [ ] ONTAP S3 エンドポイントがアクセス可能
- [ ] Snapshot ポリシーが設定済み
- [ ] NFS 経由のテストファイル書き込み/読み取り成功
- [ ] ONTAP S3 経由のテストオブジェクト書き込み/読み取り成功

### TSK-005: Databricks ワークスペースセットアップ

Unity Catalog 付き Databricks ワークスペースをデプロイ。

**構成:**
- 同一リージョンの Databricks ワークスペース
- Unity Catalog メタストア
- S3 バケットを指す外部ロケーション（またはマネージドストレージ使用）
- カタログ: `manufacturing_catalog`
- スキーマ: `factory_data`

**受入基準:**
- [ ] ワークスペースがアクセス可能
- [ ] Unity Catalog メタストアがアタッチ済み
- [ ] カタログとスキーマが作成済み
- [ ] Unity Catalog アクセスモードのクラスターが起動
- [ ] MSK への VPC 接続性確認済み

## フェーズ 2: データパイプライン開発

### TSK-006: エッジイベントシミュレーター

シミュレートされた工場エッジイベントジェネレーターを構築。

**実装:**
- 合成センサーデータと品質イベントを生成する Python アプリケーション
- DES-003 で定義された Kafka トピックに発行
- 複数デバイス、ライン、イベントタイプをシミュレート
- ペイロードメタデータを生成（合成ファイルへの参照付き）
- 設定可能なイベントレート（10-1000 イベント/秒）

**受入基準:**
- [ ] シミュレーターが有効な Avro/JSON メッセージを生成
- [ ] メッセージが Kafka トピックに出現
- [ ] イベントレートが設定可能
- [ ] 複数デバイス/ラインシミュレーションが動作
- [ ] ペイロード参照が有効な合成パスを指す

### TSK-007: ペイロードジェネレーター

FSx for ONTAP 上に合成ペイロードファイルを生成。

**実装:**
- 合成画像（メタデータ付き PNG）を生成する Python スクリプト
- 合成ドキュメント（品質データ付き PDF/テキスト）
- NFS マウント経由で FSx for ONTAP にファイル格納
- ファイルパスが Kafka メッセージの payload_uri と一致

**受入基準:**
- [ ] FSx for ONTAP 上に合成ファイル作成済み
- [ ] NFS 経由でファイルアクセス可能
- [ ] ONTAP S3 API 経由でファイルアクセス可能
- [ ] ファイル URI が対応する Kafka メッセージの payload_uri と一致

### TSK-008: Kafka から ClickHouse への取り込み

ClickHouse が Kafka から消費するよう設定。

**実装:**
- ClickHouse の Kafka Engine テーブル
- データ変換用マテリアライズドビュー
- MergeTree 宛先テーブル（DES-005）

**受入基準:**
- [ ] ClickHouse が Kafka トピックからリアルタイムで取り込み
- [ ] 5秒以内に MergeTree テーブルにデータ出現
- [ ] スキーマが DES-005 と一致
- [ ] クエリが 1 秒未満で結果を返す

### TSK-009: Kafka から Databricks へのストリーミングパイプライン

Structured Streaming パイプラインを実装。

**実装:**
- Databricks ノートブックまたは DLT パイプライン
- MSK トピックから読み取り
- Unity Catalog マネージド Delta テーブル（DES-006）に書き込み
- S3 へのチェックポイント
- スキーマ進化ハンドリング

**受入基準:**
- [ ] ストリーミングパイプラインが起動しメッセージを処理
- [ ] Delta テーブルに正しいデータが投入
- [ ] テーブルが Unity Catalog でガバナンスメタデータ付きで表示
- [ ] 正確に1回のセマンティクスが検証済み（再起動後に重複なし）
- [ ] S3 上のチェックポイントロケーション確認済み

## フェーズ 3: 検証とテスト

### TSK-010: エンドツーエンドデータフロー検証

シミュレーターからガバナンス付き分析までの完全データパスを検証。

**テスト:**
1. 10,000 イベント生成 → 全て ClickHouse AND Delta テーブルに出現を確認
2. Delta テーブルの payload_uri が FSx for ONTAP 上の実ファイルを指すことを確認
3. Unity Catalog が正しいテーブルメタデータと統計を表示することを確認
4. ClickHouse ダッシュボードクエリが正しい集計を返すことを確認

**受入基準:**
- [ ] 全システムでイベント件数一致（パイプラインレイテンシ内）
- [ ] ペイロード URI が解決可能
- [ ] Unity Catalog メタデータが正確
- [ ] データ損失なし

### TSK-011: 障害復旧テスト

パイプラインの回復力をテスト。

**シナリオ:**
1. Databricks ストリーミングジョブ停止 → 再開 → データ損失・重複なしを確認
2. ClickHouse コンシューマー停止 → 再開 → Kafka からのキャッチアップを確認
3. Kafka トピック到達不能をシミュレート → エラーハンドリングを確認
4. コンシューマーオフセットリセット → リプレイ機能を確認

**受入基準:**
- [ ] Databricks パイプラインがチェックポイントからデータ損失なしで再開
- [ ] ClickHouse がコンシューマー再起動後にキャッチアップ
- [ ] 復旧後に重複レコードなし
- [ ] 特定オフセットからのリプレイが正しい結果を生成

### TSK-012: メタデータからペイロードへのルックアップテスト

ペイロード参照整合性を検証。

**テスト:**
1. payload_uri 付きイベントを Delta テーブルからクエリ
2. 各 payload_uri について FSx for ONTAP 上にファイルが存在することを確認
3. ファイルチェックサムがメタデータと一致することを確認
4. ファイルが NFS と ONTAP S3 の両方でアクセス可能であることを確認

**受入基準:**
- [ ] payload_uri 参照の 100% が実ファイルに解決
- [ ] メタデータと実ファイル間のチェックサム一致
- [ ] 複数プロトコルでファイルアクセス可能

### TSK-013: ClickHouse コールド階層から ONTAP S3（ストレッチゴール）

ONTAP S3 バックエンドでの ClickHouse 階層化ストレージを検証。

**テスト:**
1. ONTAP S3 エンドポイントを指す ClickHouse S3 ストレージポリシーを設定
2. TTL ベースの階層移行をトリガーするのに十分なデータを挿入
3. コールドデータクエリが動作することを確認（予想されるレイテンシで）
4. ONTAP S3 上のデータが Snapshot で保護されていることを確認

**受入基準:**
- [ ] ClickHouse が ONTAP S3 を有効な S3 ストレージとして認識
- [ ] TTL ポリシーに基づきデータがコールド階層に移行
- [ ] コールド階層クエリが正しい結果を返す
- [ ] ONTAP Snapshot がコールド階層データをカバー
