## PERF-001: P99 レイテンシターゲット

### エンドツーエンドレイテンシバジェット

| セグメント | P50 ターゲット | P99 ターゲット | 測定ポイント |
|----------|------------|------------|-----------|
| エッジ → Kafka (produce + ack) | < 100 ms | < 500 ms | プロデューサーコールバックタイムスタンプ − イベントタイムスタンプ |
| Kafka → ClickHouse (consume + insert) | < 500 ms | < 2 s | ClickHouse 行タイムスタンプ − Kafka メッセージタイムスタンプ |
| ClickHouse クエリ (ホットデータ) | < 100 ms | < 500 ms | system.query_log の query_duration_ms |
| ClickHouse クエリ (FINAL dedup 付き) | < 300 ms | < 2 s | FINAL 付き query_duration_ms |
| **合計: イベント → クエリ可能** | **< 1 s** | **< 5 s** | エンドツーエンド検証テスト |

### ペイロードアクセスレイテンシ

| セグメント | P50 ターゲット | P99 ターゲット | 条件 |
|----------|------------|------------|------|
| NFS 読み取り（同一 VPC、ホットデータ） | < 10 ms | < 50 ms | SSD 階層のファイル、NFS v4.1 |
| NFS 読み取り（キャパシティプール階層） | < 100 ms | < 500 ms | キャパシティプールのファイル、初回アクセス |

## PERF-002: FSx for ONTAP 共有スループットバジェット

### スループットキャパシティ: 128 MB/s (PoC)

128 MB/s は**全プロトコルとボリュームで共有**。競合分析:

| ワークロード | プロトコル | ピーク需要 | デューティサイクル | 実効需要 |
|-----------|---------|---------|------------|---------|
| エッジペイロードアップロード（画像） | NFS | 50 MB/s | 30% | ~15 MB/s 平均 |
| エッジペイロードアップロード（動画） | NFS | 30 MB/s | 80% | ~24 MB/s 平均 |
| ClickHouse コールド階層読み取り | ONTAP S3 | 20 MB/s (バースト) | 5% | ~1 MB/s 平均 |
| FlexCache フィル (Phase B) | インタークラスター | 50 MB/s (バースト) | 10% | ~5 MB/s 平均 |
| Databricks ペイロードアクセス (ML) | NFS/S3 | 80 MB/s (トレーニングバッチ) | 定期的 | バースト |
| **合計ピーク（最悪ケース）** | | **~230 MB/s** | | **~45 MB/s 平均** |

### 推奨事項

1. **PoC**: 128 MB/s は典型的な開発/検証ワークロードに十分
2. **競合が観測された場合**: 256 MB/s にアップグレード ($174/月 vs $87/月)
3. **本番**: 512 MB/s 以上 + ボリュームごとの QoS ポリシー
4. **ML トレーニングをスケジュール**: ピークアップロード時間外に（可能であれば）

## PERF-003: ONTAP S3 認可チェーン

```
ClickHouse プロセス
    │ (S3 API コール: GET/PUT)
    ↓
ONTAP S3 エンドポイント (SVM 管理 LIF, ポート 443)
    │ (S3v4 署名検証)
    ↓
ONTAP S3 ユーザー認証
    │ (Access Key + Secret Key → SVM S3 ユーザーにマッピング)
    ↓
ONTAP S3 バケットポリシー
    │ (ユーザー、アクション、リソースに基づく Allow/Deny)
    ↓
ONTAP ボリュームパーミッション
    │ (ボリュームジャンクションパス → ファイルシステムパーミッションチェック)
    ↓
データアクセス (読み取り/書き込み)
```

## BIZ-002: Go/No-Go 判断フレームワーク

### Phase A → Phase B 移行基準

| カテゴリ | GO 基準 | NO-GO 基準 | PIVOT 基準 |
|---------|--------|-----------|-----------|
| **技術** | 全 6 PoC 成功基準クリア | テストでデータ損失検出 | — |
| **レイテンシ** | エンドツーエンド < 5s 確認 | レイテンシが常に > 30s | トピック数を削減 |
| **コスト** | 月間コスト < $1,500 | 月間コスト > $3,000 | ClickHouse Cloud → BYOC |
| **統合** | Kafka→CH + Kafka→DB 両方動作 | Kafka Engine が MSK IAM で失敗 | Kafka Connect Sink 使用 |
| **ストレージ** | FlexCache コンセプト検証済み | FSx for ONTAP が根本的に非互換 | ネイティブ S3 使用 |
| **ベンダー** | Instaclustr SE がオンプレ CH 確認 | Instaclustr がオンプレ CH デプロイ不可 | セルフマネージド CH |
| **タイムライン** | Phase A が 20 日以内完了 | Phase A が 60 日超過 | 最小限検証にスコープ縮小 |

### 判断権限

| 判断 | 権限者 | インプット元 |
|------|-------|-----------|
| Phase B Go/No-Go | アーキテクチャリード | 全 PoC 結果、コストデータ |
| オンプレハードウェア予算承認 | ビジネススポンサー (TBD) | コスト見積もり、ビジネスメトリクス |
| ベンダー選定確認 | アーキテクチャリード | Instaclustr SE エンゲージメント結果 |
| アーキテクチャピボット | アーキテクチャリード + ステークホルダー | 技術ブロッカー、代替案分析 |

## BIZ-003: ビフォー/アフターナラティブ

### 現状 (Before)

- 工場データは分離されたシステムに存在（PLC ヒストリアン、品質 DB、ファイル共有）
- 工場横断のリアルタイム可視性なし
- 品質欠陥は発生後数時間〜数日で検出
- AI/ML チームはトレーニング用にファイルを手動転送（数日のリードタイム）
- データが複数システムに重複（ヒストリアン → バッチ ETL → DWH → ML 基盤）

### 将来 (After)

- 全工場デバイスからの統合イベントストリーム（Kafka バックボーン）
- リアルタイム OEE・品質ダッシュボード（ClickHouse、< 5 秒の鮮度）
- AI/ML 向けガバナンス付きデータレイク（Databricks + Unity Catalog）
- ゼロコピーペイロードアクセス（FlexCache — データ重複なし）
- 製造データの単一の真実のソース（オンプレミス ONTAP）

### これで何が得られるか（30秒版）

> このプラットフォームは工場フロアとクラウド分析間のデータサイロを排除する。
> 品質イベントはリアルタイムで可視化される（数時間ではなく数秒）。
> AI/ML チームはデータをクラウドにコピーせずアクセスできる。
> 1つのアーキテクチャが運用ダッシュボードとガバナンス付き分析の両方に対応。
> データは1箇所に留まる（オンプレミス）。クラウドはオンデマンドでアクセスする。

## 設計レビューノート

> 本決定を[設計論点チェックリスト](08_design_concern_checklist.md)に列挙した設計上の論点に照らして確認した際のメモ。セルフレビューであり、外部レビューではない。

- **ストレージ**: セグメント別 P99 レイテンシターゲット定義。スループット競合モデル文書化。ONTAP S3 認可チェーン完成。
- **ビジネス成果**: ビジネスメトリクスが技術 SLO にマッピング。ビフォー/アフターがステークホルダーコンテキストを提供。
- **コスト**: スループットバジェット定量化。アップグレードパス明確 (128→256→512 MB/s)。
- **プロダクト判断**: Go/No-Go フレームワーク with 測定可能な基準。判断権限定義。
- **機密性チェック**: 全メトリクス、ターゲット、ナラティブはジェネリック。
