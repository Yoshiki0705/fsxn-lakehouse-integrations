## 機能要件

### REQ-F001: エッジイベント取り込み

エッジ/工場デバイスは、MQTT ブリッジまたは Kafka プロデューサーを介して、構造化イベント（品質ログ、センサー読み取り、ステータス更新）を Kafka トピックに発行できなければならない。

**受入基準:**
- イベントはスキーマとメタデータ付きで Kafka に発行される
- エッジから Kafka への少なくとも1回の配信をサポート
- イベントスキーマには timestamp、device_id、event_type、payload_reference（該当する場合）を含む

### REQ-F002: 軽量メタデータストリーミング

Kafka は軽量な構造化メタデータとイベントを伝送する。大容量ペイロード（画像、動画、ドキュメント）は Kafka を通過してはならない。

**受入基準:**
- Kafka メッセージはサイズ制限あり（推奨 ≤1 MB）
- 大容量ペイロードは別途保存し、Kafka メッセージ内で URI/パスにより参照
- メタデータにはソースパス、コンテンツタイプ、サイズ、チェックサムを含む

### REQ-F003: 大容量ペイロードストレージ

エッジデバイスからのドキュメント、画像、動画は、S3、SMB、または NFS プロトコルを使用して FSx for ONTAP に格納されなければならない。

**受入基準:**
- ペイロードは少なくとも1つのプロトコル（NFS、SMB、または ONTAP S3）でアクセス可能
- ペイロードは安定した URI またはパスで識別可能
- ストレージは異なるコンシューマー向けにマルチプロトコルアクセスをサポート

### REQ-F004: 構造化データのリアルタイム分析

ClickHouse は Kafka から高頻度構造化データを消費し、運用ダッシュボード向けにサブ秒のクエリ性能を提供しなければならない。

**受入基準:**
- ClickHouse は低レイテンシで Kafka から取り込む（エンドツーエンド < 5 秒）
- 直近データへのクエリが 1 秒未満で返る
- デバイス、ライン、品質メトリクスによる時系列集計とフィルタリングをサポート

### REQ-F005: ガバナンス付きデータレイク取り込み

Databricks は Kafka（およびオプションで ClickHouse）からデータを消費し、Unity Catalog で管理されるキュレーション済み Delta テーブルを書き込まなければならない。

**受入基準:**
- Structured Streaming が Kafka から読み取り Delta テーブルに書き込む
- Delta テーブルは Unity Catalog に登録される
- 正確に1回の処理セマンティクスを維持
- スキーマ進化をサポート

### REQ-F006: メタデータからペイロードへの参照

Delta テーブルは、Databricks が FSx for ONTAP ストレージに直接アクセスすることなく、FSx for ONTAP に格納された非構造化ペイロードへの参照（URI/パス）を含まなければならない。

**受入基準:**
- Delta テーブルカラムに payload_uri、payload_type、payload_size を含む
- ペイロード URI は認可された下流システムで解決可能
- Databricks は FSx for ONTAP の直接マウントや S3 アクセスポイントを必要としない

### REQ-F007: S3 アクセスポイント非依存

アーキテクチャは、FSx for ONTAP の S3 アクセスポイントを Unity Catalog 外部ロケーションや Delta Lake ストレージターゲットとして依存せずに機能しなければならない。

**受入基準:**
- Unity Catalog 外部ロケーションはネイティブ Amazon S3 バケットのみを指す
- FSx for ONTAP は Unity Catalog 外部ロケーションとして登録されない
- 全 Delta テーブルデータはネイティブ S3 上に存在する

## 非機能要件

### REQ-N001: PoC 実現可能性

アーキテクチャは最小限必要なコンポーネントで AWS ベースの PoC として実装可能でなければならない。

**受入基準:**
- 全コンポーネントが単一 AWS リージョンにデプロイ可能
- 総 PoC コストが見積もり可能かつ制限付き
- プライベートプレビューまたは未リリース機能への依存なし

### REQ-N002: 障害復旧

システムはストリーミングパイプラインのチェックポイント、リプレイ、障害復旧をサポートしなければならない。

**受入基準:**
- Kafka コンシューマーオフセットがチェックポイントされる
- Structured Streaming チェックポイントが耐久的に保存される
- 障害後に最終チェックポイントからパイプラインを再開可能
- 特定のオフセット/タイムスタンプからの手動リプレイが可能

### REQ-N003: 可観測性

システムは全コンポーネントの運用可観測性を提供しなければならない。

**受入基準:**
- Kafka: コンシューマーラグ、スループット、エラー率
- ClickHouse: クエリレイテンシ、取り込みレート、ストレージ使用率
- Databricks: ストリーミングメトリクス、ジョブステータス、障害アラート
- FSx for ONTAP: ストレージ容量、IOPS、スループット

### REQ-N004: セキュリティ

システムは PoC 環境に適切なセキュリティ制御を実装しなければならない。

**受入基準:**
- Kafka: SASL/TLS 認証、転送時暗号化
- ClickHouse: 認証、ネットワーク分離
- Databricks: Unity Catalog 権限、ワークスペース分離
- FSx for ONTAP: セキュリティグループ、エクスポートポリシー、保存時暗号化
- 全コンポーネント間通信は VPC 内またはプライベートエンドポイント経由

### REQ-N005: バイリンガルドキュメント

全プロジェクトドキュメントは日本語と英語の両方で維持され、内容が同期されなければならない。

**受入基準:**
- 全ドキュメントが両言語で存在する
- 同一の安定 ID を言語間で使用
- 変更時は両バージョンを同時に更新

### REQ-N006: 公開リポジトリ安全性

全コンテンツは公開 GitHub リポジトリに安全でなければならない。

**受入基準:**
- 実顧客/パートナー名なし
- 機密ビジネスコンテキストなし
- 合成データのみ（明確にラベル付け）
- プライベート URL や認証情報なし
- 機密性レビューチェックリストに合格

### REQ-N007: エビデンスベースの検証

全技術的主張は再現可能なエビデンスまたは引用ソースに裏付けられなければならない。

**受入基準:**
- 各主張は docs/references.md のソースを参照
- 仮定は明確に仮定としてラベル付け
- 未検証項目は「外部検証が必要」とマーク
- 仮説は確認済み事実と区別される
