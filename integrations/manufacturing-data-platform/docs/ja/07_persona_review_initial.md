## ペルソナ 1: プリンシパルクラウドデータアーキテクト

### 強み

1. **明確なコンポーネント分離** `[確認済み]` — Kafka（イベントバックボーン）、ClickHouse（リアルタイム分析）、FSx for ONTAP（ペイロードストレージ）、Databricks（ガバナンス付きレイクハウス）がそれぞれ明確で重複しない責務を持つ。
2. **S3 アクセスポイント依存の回避** `[確認済み]` — DEC-005 が本プロジェクトの先行検証（Part 2 ブログ、SHARED-KNOWLEDGE.md）で文書化された S3 AP 制限からアーキテクチャを明示的に切り離している。
3. **Delta テーブルにネイティブ S3** `[確認済み]` — DEC-001 が Unity Catalog の外部ロケーションはネイティブクラウドストレージのみサポートする制限に正しく対応（REF-020、REF-021、REF-022）。
4. **メタデータ/ペイロード分離** `[確認済み]` — REQ-F002 が Kafka メッセージサイズを制限（≤1 MB）し、URI でペイロードを参照。製造データプラットフォームで実証済みパターン（REF-033）。
5. **正確に1回のストリーミングセマンティクス** `[確認済み]` — Structured Streaming + Delta Lake が正確に1回の保証を提供（REF-002、REF-004）。

### 懸念事項

1. **ClickHouse デプロイモデル未定義** `[前提]` — アーキテクチャは ClickHouse が同一 VPC 内で利用可能と仮定しているが、Cloud / BYOC / セルフマネージドのいずれかを指定していない。それぞれ運用、コスト、統合面で異なる影響がある。
2. **Kafka → ClickHouse 取り込みパターン未指定** `[未決事項]` — Kafka Engine（組み込み）、ClickPipes（マネージド）、Kafka Connect のいずれで取り込むか？各々にレイテンシと信頼性のトレードオフがある。
3. **ClickHouse と Databricks 間のデータ整合性確認なし** `[仮説]` — 両方が Kafka から独立して消費する場合、障害時に乖離が発生する可能性がある。整合性確認の必要性はユースケースによる。
4. **オブザーバビリティアーキテクチャ未設計** `[前提]` — REQ-N003 がメトリクスを列挙しているが、オブザーバビリティプラットフォーム（CloudWatch、Grafana、Databricks SQL Analytics 等）を定義していない。

### 必要な検証

| # | 検証項目 | ステータス |
|---|---------|-----------|
| 1 | Kafka → Databricks Structured Streaming で UC 管理 Delta テーブルへの書き込み | 実現可能確認済み（REF-001、REF-003） |
| 2 | Kafka → ClickHouse 5秒以下のエンドツーエンドレイテンシ | PoC での計測が必要 |
| 3 | ClickHouse → Databricks バッチエクスポート（Spark コネクタ） | 実現可能確認済み（REF-010、REF-011） |
| 4 | FSx for ONTAP マルチプロトコルペイロードアクセス（下流システムから） | 確認済み（既存プロジェクト検証） |
| 5 | チェックポイントによるエンドツーエンド障害復旧 | PoC での検証が必要 |

### 必要な設計変更

- ClickHouse デプロイモデルの指定（Cloud / BYOC / EC2 セルフマネージド）
- Kafka → ClickHouse コネクタの選択を定義
- データ整合性確認戦略の追加、または不要である理由の明示的文書化

### 未決事項

- PoC vs 本番でのイベントボリューム（イベント/秒）の想定は？
- エッジから ClickHouse ダッシュボードまでの最大許容エンドツーエンドレイテンシは？
- PoC で Amazon MSK と MSK Serverless のどちらを使用するか？
- Confluent Tableflow（REF-005、REF-061）はカスタム Structured Streaming の代替候補か？

### 本番準備状況評価

**PoC 実施可能（ギャップあり）** — コアデータフローはリファレンスにより技術的に検証済み。デプロイモデルと運用設計は PoC 実行前に仕様化が必要。

## ペルソナ 2: 製造エッジデータアーキテクト

### 強み

1. **MQTT + Kafka プロデューサーパターン** `[確認済み]` — 業界リファレンスで検証された標準 IIoT パターン（REF-032、REF-033）。
2. **メタデータ/ペイロード分離** `[確認済み]` — REQ-F002 が Kafka を軽量メタデータに正しく制限。大容量ペイロード（画像、動画、品質ドキュメント）は Kafka をバイパスし FSx for ONTAP に直接格納（REQ-F003）。
3. **イベントスキーマに payload_reference を含む** `[確認済み]` — REQ-F001 の受入基準にイベントと格納済みペイロードを紐づける `payload_reference` フィールドを含む。

### 懸念事項

1. **エッジバッファリングとリトライが未設計** `[未決事項]` — 工場フロアから Kafka に到達できない場合どうなるか？ローカルバッファ（永続化付き MQTT ブローカー、ローカルファイルシステムキュー等）はあるか？
2. **ペイロードアップロードメカニズム未定義** `[前提]` — REQ-F003 はペイロードが S3/SMB/NFS 経由で FSx for ONTAP に格納されると述べるが、アップロードフロー（エッジからの直接書き込み、ゲートウェイ、ストアアンドフォワード）を指定していない。
3. **重複排除戦略なし** `[未決事項]` — at-least-once 配信（REQ-F001）は重複の可能性を意味する。ClickHouse と Databricks での重複検出と処理方法は？
4. **時刻同期が未対処** `[仮説]` — 製造環境では NTP ドリフトが頻繁に発生。event_timestamp がエッジで生成される場合、クロックスキューが順序問題を引き起こす可能性がある。
5. **ペイロード完全性検証なし** `[未決事項]` — REQ-F002 がチェックサムに言及するが、アップロード後の検証がいつ/どのように行われるか指定していない。

### エッジパイプライン前提

| # | 前提 | 誤りの場合のリスク |
|---|------|------------------|
| 1 | エッジデバイスが Kafka/MSK エンドポイントに到達可能 | パイプライン停止；ローカルバッファリング未指定 |
| 2 | 大容量ファイルを中断なく FSx for ONTAP にアップロード可能 | 部分アップロードがペイロードストアを破損 |
| 3 | MQTT ブローカーがバックプレッシャーを適切に処理 | Kafka 停止時のメッセージ損失 |
| 4 | デバイス単位でイベント順序が保持される | ClickHouse でのイベント順序逆転 |

### 必要なメタデータスキーマ

以下のフィールドは確認済み（REQ-F001、REQ-F002）:

```json
{
  "event_id": "uuid",
  "timestamp": "ISO8601",
  "device_id": "string",
  "event_type": "string",
  "payload_reference": "s3://or nfs:// URI (nullable)",
  "content_type": "string",
  "payload_size_bytes": "integer",
  "checksum_sha256": "string"
}
```

**不足フィールド** `[未決事項]`:
- `factory_id` / `line_id` — マルチ工場デプロイに必要
- `sequence_number` — デバイス内の順序付けに必要
- `retry_count` — 重複排除に必要

### 障害シナリオ

| シナリオ | 現在の設計 | ギャップ |
|---------|-----------|---------|
| Kafka 不通 | 未対処 | エッジバッファが必要 |
| FSx for ONTAP 書き込み失敗 | 未対処 | リトライ + 部分アップロードクリーンアップが必要 |
| 重複イベント配信 | at-least-once を認識 | 重複排除戦略なし |
| ネットワーク分断（エッジ ↔ クラウド） | 未対処 | ストアアンドフォワードが必要 |
| 大容量ファイルアップロード中断 | 未対処 | マルチパート + 再開が必要 |

### PoC 検証タスク

1. 合成エッジイベントによる Kafka プロデューサーのシミュレーション
2. FSx for ONTAP への大容量ファイルアップロードシミュレーション（S3 マルチパート経由）
3. イベント→ペイロード紐づけの検証（Delta テーブルクエリ、URI 経由でペイロード取得）
4. ネットワーク中断シミュレーションとデータ損失の計測
5. エンドツーエンドレイテンシ計測：エッジイベント → ClickHouse クエリ結果

## ペルソナ 3: Databricks ガバナンスアーキテクト

### 強み

1. **Delta テーブルにネイティブ S3** `[確認済み]` — DEC-001 が既知の Unity Catalog 制限を回避。ネイティブ S3 上の Delta テーブルは完全にガバナンス適用。
2. **Kafka → Structured Streaming → Delta** `[確認済み]` — 十分にサポートされた本番実績パターン（REF-001、REF-003、REF-007）。
3. **メタデータ→ペイロード参照パターン** `[確認済み]` — REQ-F006 が Delta カラムに payload_uri を格納し、Databricks が FSx for ONTAP に直接アクセスする必要なし。
4. **FSx for ONTAP の UC 外部ロケーション登録なし** `[確認済み]` — REF-020、REF-022 で文書化された非サポートパターンを正しく回避。

### 懸念事項

1. **ClickHouse → Databricks 統合が完全に未指定** `[前提]` — REF-010 が Spark ClickHouse Connector の存在を確認するが、ユースケース（バッチエクスポート？リアルタイム同期？集約サマリー？）が未定義。
2. **スキーマ進化戦略が未定義** `[未決事項]` — REQ-F005 がスキーマ進化サポートに言及するが、エッジスキーマ変更が Kafka → Delta にどう伝播するか未指定。
3. **Unity Catalog 権限モデルが未設計** `[前提]` — 誰がどのテーブルを読み書きできるか？UC 内で工場別データセットをどう分離するか？
4. **ストリーミングテーブル vs マネージドテーブルの選択が未決** `[未決事項]` — Databricks はストリーミング取り込みに対してストリーミングテーブルと標準マネージドテーブルの両方をサポート。各々にチェックポイントと DLT の影響が異なる。

### Unity Catalog 互換性評価

| 観点 | ステータス | 備考 |
|------|----------|------|
| ネイティブ S3 上の外部ロケーション | ✅ 互換 | DEC-001 |
| キュレーション済みデータのマネージドテーブル | ✅ 互換 | 標準パターン |
| ストレージ資格情報（IAM ロール） | ✅ 互換 | 標準パターン |
| リネージ追跡 | ✅ 互換 | マネージドテーブルで自動 |
| S3 互換エンドポイント（FSx for ONTAP） | ❌ 未使用 | 正しく回避 |
| ノートブックからのペイロードアクセス | ⚠️ 間接 | payload_uri を使用して boto3/requests 経由、UC ガバナンス外 |

### 取り込みパターン推奨

**主要パス**: Kafka → Databricks Structured Streaming → ネイティブ S3 上の Delta Lake マネージドテーブル → Unity Catalog ガバナンス

**副次パス**（集約データ用）: ClickHouse → Spark ClickHouse Connector → Delta Lake（バッチ、スケジュール）

**ペイロードアクセス**（ノートブックで必要な場合）: boto3 + FSx for ONTAP S3 または クラスター init スクリプト経由の NFS マウント（UC ガバナンス外）

### 回避すべき非サポート前提リスト

| # | 回避すべき前提 | 理由 |
|---|--------------|------|
| 1 | FSx for ONTAP を UC 外部ロケーションとして登録 | S3 互換エンドポイント非サポート（REF-020） |
| 2 | FSx for ONTAP に Delta テーブルを書き込み | アトミックリネーム、条件付き書き込み不可 |
| 3 | ペイロードファイルに対する UC 直接ガバナンス | UC はテーブルを管理、任意のファイルストアではない |
| 4 | UC ストレージ資格情報で S3 アクセスポイントを使用 | セッションポリシー制限（SHARED-KNOWLEDGE.md） |

### ガバナンスリスク評価

**低リスク** — アーキテクチャがガバナンス対象データ（S3 上の Delta テーブル）と非構造化ペイロード（FSx for ONTAP）を正しく分離。UC は構造化メタデータ層をガバナンス。ペイロードガバナンスには別メカニズム（IAM、エクスポートポリシー、アプリケーションレベル制御）が必要。

## ペルソナ 4: NetApp FSx for ONTAP アーキテクト

### 強み

1. **明確な技術的位置づけ** `[確認済み]` — FSx for ONTAP がマルチプロトコルアクセス、Snapshot、エンタープライズデータ保護が必要な大容量非構造化ペイロードに特化して位置づけ。
2. **過度な拡張なし** `[確認済み]` — アーキテクチャが FSx for ONTAP を Delta Lake ストレージとして使用しようとしていない（アトミックリネーム制限で失敗することが既知）。
3. **製造環境でのマルチプロトコルアクセスの価値** `[確認済み]` — 工場システムは NFS/SMB 経由で書き込み、分析コンシューマーは S3 プロトコル経由で読み取り可能。実用上の利点。
4. **メタデータ/ペイロードパターンが FSx for ONTAP の価値を維持** `[確認済み]` — ペイロードが完全な ONTAP データサービス（Snapshot、SnapMirror、重複排除、圧縮）とともに FSx for ONTAP に残りつつ、メタデータは Kafka/Delta を流れる。

### 懸念事項

1. **ONTAP S3 プロトコル vs S3 アクセスポイントの区別が不明確** `[前提]` — DEC-005 は「S3 アクセスポイント依存なし」と述べるが、ペイロードが下流コンシューマーから ONTAP ネイティブ S3 プロトコル、NFS、SMB のいずれでアクセスされるか明確にしていない。
2. **データ保護戦略が未詳細** `[未決事項]` — Snapshot ポリシー、SnapMirror ターゲット、保持期間、復旧手順が未定義。
3. **ストレージサイジングなし** `[未決事項]` — ペイロードボリューム（GB/TB）、増加率、階層分布（SSD vs キャパシティプール）の見積もりなし。
4. **PoC データ分離の FlexClone 未言及** `[仮説]` — FlexClone が本番相当のペイロードデータをストレージ複製なしに PoC テスト用に即座にコピー提供可能。

### FSx for ONTAP 価値評価

| 機能 | 本アーキテクチャへの適用 | 正当性 |
|------|:---------------------:|--------|
| マルチプロトコル（NFS/SMB/S3） | ✅ 高 | 工場は NFS/SMB で書き込み、分析は S3 で読み取り |
| Snapshot | ✅ 高 | ポイントインタイムのペイロード復旧、テスト |
| SnapMirror | ✅ 中 | 重要ペイロードデータの DR |
| FlexClone | ✅ 中 | PoC データプロビジョニング、開発/テスト分離 |
| 重複排除 | ⚠️ 状況による | 類似ペイロードバージョンが存在する場合に有用 |
| 圧縮 | ✅ 中 | 大容量ドキュメント/画像ペイロードのコスト削減 |
| FabricPool | ✅ 中 | 古いペイロードを S3 Glacier に階層化 |
| SnapLock | ⚠️ 状況による | 規制対応の保持が必要な場合のみ |

### ネイティブ Amazon S3 との比較

| 考慮事項 | FSx for ONTAP | ネイティブ S3 |
|---------|:-------------:|:----------:|
| マルチプロトコル（NFS/SMB/S3） | ✅ | ❌ S3 のみ |
| 既存工場 NFS/SMB 統合 | ✅ 変更不要 | ❌ 移行が必要 |
| スペース効率の良いスナップショット | ✅ ボリュームレベル | ⚠️ S3 バージョニング（オブジェクト単位、大規模でコスト高） |
| 即時クローニング（FlexClone） | ✅ | ❌ フルコピーが必要 |
| クロスリージョンレプリケーション | ✅ SnapMirror | ✅ S3 レプリケーション |
| コスト（大容量ペイロードストア） | ⚠️ GB 単価高め | ✅ GB 単価低め |
| 運用複雑性 | ⚠️ ONTAP 管理 | ✅ フルマネージド |
| 分析プラットフォームとの統合 | ⚠️ S3 AP または NFS マウントが必要 | ✅ ネイティブ |

### 必要なストレージテスト（PoC）

1. NFS 経由で 100 個の混合ペイロード（画像 5–50 MB、ドキュメント 1–10 MB）をアップロード
2. Lambda 関数から ONTAP S3 プロトコル経由で同じペイロードを読み取り
3. ペイロードバッチアップロード前後に Snapshot を作成
4. Snapshot から特定ファイルを復元
5. 類似画像セットでの重複排除率を計測
6. Delta テーブルメタデータからの payload_uri 解決を検証

### NetApp ポジショニングノート

- FSx for ONTAP は本アーキテクチャにおいて、マルチプロトコルアクセスが必要な大容量非構造化データのペイロードストアとして明確な価値を付加
- アーキテクチャは FSx for ONTAP を Delta Lake ストレージレイヤーとして過度にポジショニングすることを正しく回避（既知の制限）
- メタデータ/ペイロード分離パターンにより、FSx for ONTAP がその強み（データ保護付きエンタープライズファイルサービス）の領域で動作可能
- S3 アクセスのみが必要なペイロードにはネイティブ S3 がコスト効率的であることを明示的に文書化すべき — FSx for ONTAP はマルチプロトコルまたは ONTAP データサービスが必要な場合にのみ正当化
